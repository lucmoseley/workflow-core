# v1.3.14

## What changed

The code-standards base your reviews read has changed:

- §0: a stack clause binds only the files its tool reads: a Vitest clause
  binds the tests Vitest runs, never a pytest file beside them (workflow-core#947).
- §0 has a new "How a rule enters": a rule enters because it is right, never
  because the code already follows it (workflow-core#1312), and it binds every repo the
  plugin runs in, each taking its clean-up through a required `[act]` step
  (workflow-core#1406, workflow-core#1439). A rule whose breach exists only in a change, never in a
  standing tree, has nothing to list, so it enters with a `[notice]` in
  place of that step (workflow-core#1495).
- §0: a changes-table row's reason names one of five merit grounds — false
  findings, no defect behind the rule, a tool already enforcing it, a stack
  it cannot fit, or code the repo never has or does. A reason that the code
  does not do it yet, lacks the setup, or would cost work to bring up is
  itself a finding, and so is a route row that sends code to a kind it is
  not (workflow-core#1439).
- §0's **hard** now means no code breaks the rule without a written reason,
  in place of "the corpus has no unexplained counterexample"; a breach
  elsewhere in the code is a second finding, never a reason to downgrade
  this one (workflow-core#1312).
- §S5 is new and **hard**: a script sets the shell options its kind needs
  (workflow-core#1315, workflow-core#1331). A run script sets `-uo pipefail`; one that must stop at
  its first failure also sets `-e`, and a gate or other hook leaves `-e`
  off; a sourced library sets nothing; a husky hook sets `-e` alone; any
  other `sh` script sets `-u` alone.
- §T1: where your §W hands the return-type rule to a linter, a review
  raises only what that linter cannot reach, such as a non-component
  function in a `.tsx` file (workflow-core#1335).
- §T4 (`interface` for an object shape, `type` for a union or a function
  type) is now **hard**, where it was judgement (workflow-core#1327). Where your §W
  switches on Biome's `style/useConsistentTypeDefinitions`, a review leaves
  the object-shape limb to it.
- §0 has a new "The design vocabulary": short definitions of module,
  interface, seam, adapter and depth (workflow-core#1360). "Interface" there means
  everything a caller must know, not the TypeScript keyword.
- §X5 is new, at **judgement**: a test builder with a nullable or optional
  parameter states in a docstring what that parameter's absence means,
  unless its own body shows it (workflow-core#1330).
- §X6 is new and **hard**: a module test checks what the module's interface
  returns or does, never its internal state or how often its internals
  were called. A spy on captured output or on an injected dependency
  conforms (workflow-core#1372).
- §X7 is new, at **judgement**: when a module is deepened or replaced, the
  old module's unit tests that the new module's tests now cover are deleted
  in the same change; program tests stay (workflow-core#1372).
- §G8 is new, at **judgement**, for every code kind: where the repo has a
  `GLOSSARY.md`, a new name for a concept it defines uses its term and none
  of its *Avoid* words; a homonym is outside the rule. `/code-review` and the
  code-review rules guard now hand the Standards axis your `GLOSSARY.md`
  wherever one exists (workflow-core#1373).
- §N9 is new, at **judgement**, for program code: a function returns its
  result rather than changing an object or array it was passed. The
  exception is a caller-owned accumulator or counter passed in for that
  purpose, said at the parameter: a JSDoc `@param` description opening
  `accumulator:`, or in Python a docstring sentence opening with the
  backticked parameter and calling it the caller's accumulator (workflow-core#1375).
- §G7 is new, at **judgement**, for program, library and shell code: every
  injected seam — a dependency parameter, a port, or an env var standing in
  for a binary, a file or a clock — has a second adapter, and a test fake
  counts. Otherwise a comment at the seam names the caller that will supply
  one, or the seam goes and the dependency is created in place. A tunable
  env var is outside it; a second adapter outside the repo, said at the
  seam, is the good reason to differ (workflow-core#1374).
- §G6 is new and **hard**, for program, library and test code: nothing is
  exported only for its tests. Not test-only: a `main` a program carrying a
  `require.main` guard exports for `run-in-process`; test support, a
  testkit, harness, fixture, stub or fake module; and a module whose header
  carries `Unbuilt caller: <caller> (#N)`. §N7's house clause keeps only its
  spelling, a single trailing `module.exports = { … }`, and its comment
  escape can never name a test (workflow-core#1376).
- `check-code-standards.js` counts no test or test support as an export's
  consumer (workflow-core#1361), and it judges exports in a repo keeping no local
  standards file, where it used to skip (workflow-core#1376).
- §G3 now says how a Python lint suppression gives its reason, where the repo
  has ruff's tell (`ruff.toml`, `.ruff.toml` or a `[tool.ruff]` table in
  `pyproject.toml`): `# noqa: <code> - <reason>`, one code per directive, the
  directive inline on the line it excuses — never a bare `# noqa`, nor a
  file-top `# ruff: noqa` or `# flake8: noqa` (workflow-core#1284). The reason may instead
  head the code it excuses.
- §N7's one-env-var rule now covers only an external binary a test needs to
  stub, or a machine running the code may lack (workflow-core#1283). Outside it: `git`,
  the repo's own runtimes and their package managers (`node`, `npm`,
  `python3`) and standard system tools (`free`, `tar`, `sh`, `bash`, `setsid`
  and their like). `ps` enters the rule, at `WFC_PS`, and `gitleaks` takes
  `WFC_GITLEAKS`. A test that needs a fake of an exempt one puts it ahead of
  the real one on `PATH`, or passes the code under test an exec function.
- §X3's run-in-process house clause binds Node programs only, so a test
  that is not a Node program is never asked to load `run-in-process.js`
  (workflow-core#1266, shipped in v1.3.13).
- §N2's header block now binds library code (`lib/**`, the non-component
  modules under `app/**`) and hook modules too: each opens with a block
  comment giving its filename, one line on what it is, then why and the
  ticket (workflow-core#1406). A presentational component still owes none.
- The lighter tier now takes §T1's non-component limb: a function in a
  presentational `.tsx` file that is not a component, such as a page's
  `generateStaticParams`, annotates its return type (workflow-core#1406).
- §T4 binds declared types only: a type literal written inline in a
  signature is outside it (workflow-core#1406).
- §N3: a program never takes another language's family prefix unless it
  keeps that family's contract, so a Python hook that always exits 0 is
  never a `check-*` (workflow-core#1406).
- §G5 names shell's own convention as its fallback: lower snake_case
  functions and variables, UPPER_SNAKE constants and environment variables
  (workflow-core#1406).
- §G2 binds a chosen value wherever it sits, not only at module scope: a
  parameter's default, a call-site argument or a local name states where it came from or that it is a
  guess. Several sites holding one value for one reason take it from one
  constant (workflow-core#1440).
- §N7: one of `git`, the runtimes or the system tools enters the one-var
  rule when tests feed it chosen output, where it used to enter when tests
  routinely stubbed it; and code that runs `python3` handles its absence
  (workflow-core#1406).
- §X3's Vitest clause now mints a temp directory, and a git repo only where
  the program reads git state (workflow-core#1406).
- §T8 is new and **hard**, with your `tsconfig.json`: the type check runs
  with `noUncheckedIndexedAccess`, so code reading a list or map entry
  handles its absence on purpose (workflow-core#1316, workflow-core#1380). A finding is cleared only by
  one of the shapes §T8 lists; `!`, a behaviour-changing default, `?.` where
  the code used to throw, a cast dropping `undefined`, `@ts-ignore` and a
  dead branch are each a breach. §N8 now holds programs to it too. Test
  files stay outside it.
- §N8 no longer excepts a catch binding typed `any` (workflow-core#1329). The binding
  stays `unknown` and is read through `instanceof Error` or `caught`
  (`scripts/lib/caught.js`, new on the helper surface), and a cast of it is
  an unchecked assertion.
- §0 "How a rule enters" now settles what the plugin ships as well as what
  the base asks: whether your repo already follows a practice, or has the
  setup it needs, is never a reason to leave it out or soften it (workflow-core#1380).

The core's own `biome.json` now refuses a JS or TS function taking more
than four positional parameters in `scripts/**` and
`.claude/skills/*/scripts/**`, as it already did in `app/**` and `lib/**`
(workflow-core#1313). The base carries no rule on parameter counts.

The core's `ruff.toml` now caps Python functions at four positional
parameters too, with ruff's `PLR0917` (workflow-core#1314). The pre-commit
Python gate lints with that file wherever your repo has no ruff config of
its own (a root `ruff.toml`, `.ruff.toml`, or `[tool.ruff]` in
`pyproject.toml`), so there it now refuses a commit that adds a function
taking five or more positional parameters, or lengthens one.

Two checkers now ship and run from your pre-commit
hook (workflow-core#1380). `check-skill-frontmatter.js` refuses a commit staging one of
your own `.claude/skills/<name>/SKILL.md` whose frontmatter a strict YAML
parser rejects (workflow-core#887). `check-workflow-permissions.js` refuses a commit
adding or editing a `.github/workflows/` file in which a job holds a write
scope beyond
`issues: write`, declares no `permissions:` block, or runs `git commit` or
`git push`.

`check-cli-args.js` now ships and runs from your pre-commit hook too
(workflow-core#1532). It refuses a commit adding or editing a top-level `scripts/*.js`
that reads its command line without a strict parser, so `--help` or an
unknown flag runs the script's default action (workflow-core#920). `node:util`'s
`parseArgs` passes unless called with `strict: false`, and commander unless
told `allowUnknownOption`; any other parser, or a wrapper passing its argv
through, takes a `cli-args-exempt: <why>` comment. A script your commit
leaves untouched only warns.

The `domain-modeling` skill now runs a concision pass before an ADR is
committed.

The pre-commit stack gains a format gate (workflow-core#1332): shfmt at `-i 2 -ci` over
a commit's staged `scripts/**/*.sh` and husky hooks, and `ruff format` over
its staged `.py`, each judged on the staged blob and over the whole file.
shfmt is npm's `@wasm-fmt/shfmt`, read from your repo's own `node_modules`,
and ruff is the one on `PATH`. A formatter that is not installed refuses a
commit touching its files, naming the line that installs it (workflow-core#1463). It
skips that half instead only where a workflow under `.github/workflows/`
runs the formatter. The PostToolUse write hook formats a written shell or
Python file the same way.

The ruff gate's refusal now offers `ruffExclude` for vendored or
third-party code alone (workflow-core#1463). A missing ruff no longer passes that gate:
it refuses a commit touching a `.py`, naming the line that installs ruff,
unless a workflow under `.github/workflows/` runs `ruff check`, where it
still warns and passes (workflow-core#1563). The shellcheck and actionlint gates still
skip a missing binary, but their warning now names the workflow that runs
the tool, or says none does, instead of claiming `ci.yml` runs it (workflow-core#1629).

The core's `ruff.toml` now also selects `BLE001`, `E4`, `E7` and `RUF100`
(workflow-core#1333). Where your repo has no ruff config of its own, the pre-commit
Python gate now refuses a commit that adds a blind `except Exception`
carrying no `# noqa: BLE001`, a bare `except:` carrying no `# noqa: E722`, a
one-line multiple import, an import below other code, a lambda bound to a
name, `l`, `O` or `I` as a name, or a `noqa` naming a code that does not fire
on its line.

The core's `ruff.toml` now selects pep8-naming, `N` (workflow-core#1443), so base §G5's
Python scheme is ruff's to refuse. Where your repo has no ruff config of its
own, the gate now refuses a commit that adds a name breaking it, or an
exception class whose name does not end in `Error`.

The architecture scan is switched on in every repo (spec workflow-core#1348):

- A daily count, run at session start:
  `scripts/report-arch-scan-due.js` sums the net line growth of your ten
  most-committed code files since your last scan. At or over the threshold (8,750 lines
  to start), it files or refreshes one `takes:implement` issue,
  *Architecture scan due*, in your own tracker. It files nothing while a
  scan is in flight, and an issue closed without a scan is not refiled
  until growth counted from the close reaches the threshold again. A
  failure is one line in the guard-error log, never a failed session start.
- The new `architecture-scan` skill runs from that issue: `scan <issue>`
  files a wayfinder map of deepening candidates, and `close <map>`
  recalibrates the threshold from how many were built.
- `docs/data/arch-scan-runs.jsonl` is the run log the skill appends to,
  one JSON line per scan or close, and the counter's window starts at its
  newest scan.
- `.claude/workflow-core.json` takes an optional `archScan` object:
  `threshold`, a positive integer that overrides the learned threshold, and
  `exclude`, an array of git pathspec globs (`data/**`) your count leaves
  out. Neither switches the scan off. A malformed value is never read as
  unset: `--dry-run` refuses it, and the daily count logs it and files
  nothing.
- `node <plugin root>/scripts/report-arch-scan-due.js --dry-run` prints what
  a reading would see and files nothing.

Every upgrade now brings each core-owned file to the plugin's current form,
as init does, whether or not a note asks (workflow-core#1501): the husky hooks, the helper
scripts (`scripts/browse.py`), `.claude/workflow-core.md`, the core's
`.claude/settings.json` keys, the `.gitignore` block, the context-cost row and
the tracker's labels.

- A helper that is missing, stale or edited locally is rewritten to the
  plugin's copy, and a line says any local edit is gone (workflow-core#1453).
- `settings.json` is written with 2-space indents, and left as it is where
  every key is already current (workflow-core#1484).
- The labels sync on every upgrade, with one `gh label list` and a create
  only for a label missing or changed. With no `tracker` in
  `.claude/workflow-core.json` the tracker comes from your `origin` remote,
  as init's does; where neither resolves, a line says the sync was skipped
  (workflow-core#1484).
- A hook of your own under a shipped name — one with no `WFC_PLUGIN_ROOT`
  line — is left alone at init and at every upgrade, with a line saying the
  core's gate for it does not run.

The delivery mod can no longer be switched off for a whole repo (workflow-core#1467). It
tells the model what a session must act on, release requests among them, so
`"mods": {"wfc-delivery": false}` in `.claude/workflow-core.json` now leaves it
running. The liveness mod keeps its `mods` switch, since it only displays.
`readConfig` now warns where `mods` names `wfc-delivery`, names a mod it does
not know, or gives no object of booleans; each mod still reads such a value as
on.

Your own hooks, guards and checkers are now held to the core's registry rule
(workflow-core#1456). `guard-registry-atomicity.sh` refuses a commit
adding a `scripts/guard-*` or `scripts/check-*.js` of yours, or changing the
hooks your `.claude/settings.json` runs, unless it carries what registers the
member: a `hooks` row in `.claude/registrations.json` pinning each settings
registration, a `registeredElsewhere` or `calledElsewhere` entry for one no
hook or caller runs, an entry in `.claude/guard-fire-needles.json`, and a
sibling test, `<name>.test.<ext>` for any of `ts`, `js`, `mjs`, `cjs` or
`py`. `upgrade` writes both empty where absent and never touches them after.
`check-registrations.js` is the whole-repo form, run by `.husky/pre-commit`
under `--against HEAD`, so a gap you already have only warns.

`runCheck` now awaits a `run(ctx)` that returns a Promise, so a checker that
fans its GitHub reads or suites out in parallel can report through it (workflow-core#1586).
A rejection reads as a throw, one `run` started but never awaited included:
`ctx.skip` gives SKIP, `ctx.broken` gives BROKEN, and anything else BROKEN
with the stack. A Promise that never settles is BROKEN, where it used to exit
0 having checked nothing. A spec declaring `against` with an async `run` is
BROKEN until `--against` gains an async path.

`animate` hard rule 6 now reads the design vault's library,
`~/design-vault/data/gallery.json`, where your repo has no
`docs/inspiration/catalogue.json`, in place of falling back to the brand sheet
alone (workflow-core#1455). It reads the entries judged for your repo's key in the vault,
the one your `CLAUDE.md` names for the design vault, and has the founder judge
any other through `design-round` §1a before using it.

`check-stranded-research.js` reads its accepted-lost allowlist from your repo's
own `docs/stranded-research-allowlist.json`, no longer the core's (workflow-core#1608). With no file,
nothing is accepted and nothing reports stale; a file that does not parse, or
an entry with no `paths` or `reason`, is BROKEN.

A change to code your repo declares sensitive now gets a deeper review
(workflow-core#1612). Declare it as `sensitivePaths` in `.claude/workflow-core.json`: a
list of areas, each with a `name` and a one-line `description`, and optional
`globs`, `focus`, `examples` and `live`, which reads as false where absent. A
change matching an area's globs owes the escalated review at any size and in
any file type: the Standards and Spec runs plus a focused run against the
area's `focus`, and an attacker run besides where the change alters an access
rule or a money calculation. `review-hold-gate.sh`, new in `.husky/pre-commit`,
refuses a session's shared-tree commit on such a path until a staged review of
exactly that tree is recorded. A session judges an area with no globs from its
description. The Stop nag and the push warning name the tier owed, and each
such review leaves a `**Review tier:**` and a `**Review findings:**` comment on
the ticket in hand. On a `live` area, a change too large for one reviewer has
the session ask the founder for an ultrareview, keeping the change off shared
`main` until he answers, and run it on his yes. Until the key is set, every
review says nothing can escalate; `[]` declares none.

The plugin now ships `docs/environment.md`, the machine's measured limits that
the suite, admission and scratch guards enforce (workflow-core#1452). Every doc a guard's
text, a checker's report or a skill names is spelled at the plugin root, so
`docs/effort-guide.md` and `docs/environment.md` open the plugin's copy rather
than a path in your tree. Where your repo keeps its own `docs/environment.md`,
the guards no longer point at it. Nothing to do.

A commit is now refused while your tree tracks something a gate guards but
that gate's switch is off (workflow-core#1506). `check-gate-switches.js`, new in
`.husky/pre-commit`, reads the whole index, not the staged paths, so a subject
already in your tree is refused at your next commit. It checks four: a test
file (`*.test.{js,mjs,cjs,ts,tsx,py}`, `test_*.py`, `*_test.py`) with no
`commands.test`; `docs/reference-roadmap.html` with `roadmap` off; the
operating manual or a `docs/doc-map.md` §B entry with `governance` off; your
brand sheet plus anything under `app/` with `site` off. A first `init-adopter.js`
run with no `--modules` now switches on each module whose subject the tree
already holds. The new repo's first map no longer carries the reminder to
declare `commands.test`.

      to those kinds a §N2 header, before a review raises each one (workflow-core#1406).
