# v1.3.12

## What changed

`count-guard-fires.js` can now count a guard you register in your own
`.claude/settings.json` (workflow-core#1267). Key it in `.claude/guard-fire-needles.json`
at your repo root, the same shape as the core's
`scripts/guard-fire-needles.json` but holding `guards` only:

```json
{ "guards": { "guard-example.sh": { "needles": [
  { "id": "example", "kind": "warn", "text": "a phrase the guard prints" }
] } } }
```

- A missing file means you have no needles of your own, and is not an error.
- A key the core's file already holds is refused, exit 2, naming the key: the
  core owns its own guards' words.
- Anything but a `guards` object (a `candidates` block, a `guards` array) is
  refused, exit 2, rather than dropped unread.
- A key no hook file registers is warned as stale, naming the file that holds
  it. An unkeyed guard's warning now names the file its entry belongs in:
  yours for a guard only your settings register, the core's for one the
  plugin registers.

The code-standards base your reviews read has changed (workflow-core#1266): a route row in
your local file may send a path to "none", binding no section, only where your
repo neither writes nor runs that code — vendored, generated, or a reference
export nothing imports. The row says which of the three and cites its ruling.
A "none" row over code your repo writes or runs is now itself a finding.

A release check that fails having written only to stdout now prints that
output under the refusal, rather than stopping at the colon (workflow-core#1268).

      route it to the sections that bind it.
