# v2.1.0

## What changed

This release moves every repo onto the landing queue and the worktree model,
by turning the `landing` module on (workflow-core#2412, workflow-core#4252). With it on, each session
works in its own worktree under `.claude/worktrees/`, cut from `origin/main`,
and lands by pushing its own `queue/<name>` ref
(`node scripts/lib/resolve-core.js scripts/session-checkout.js land`). The
queue lander tests each batch with your `commands.test` in a worktree of its
own, moves `main` only to a sha that passed, and drops a member that fails
alone to `dropped/<name>` with a fix ticket (workflow-core#4458). The main checkout takes no
edits or commits; a levelling step fast-forwards it to `origin/main` after
each landing (workflow-core#4229). A repo declaring no test command lands untested, as it
has nothing to fail (workflow-core#2412).

This release also deletes the shared-tree guards: the stale write-back gate,
the stale-script warning, the commit route's lock wait and retry, the pull
guard's discard limb (workflow-core#4251), and the file-claim refusal, now a warning
(workflow-core#4249). With `landing` off, every session still shares the main checkout, and
nothing now stands in for them. Turn `landing` on with the last three [act]s
below, in the same sitting as this upgrade.

Your pre-commit's and init's check of `commands.check_staged` now follows npm's
workspace selectors (workflow-core#4041): `-w` or `--workspace` by member name, directory or
parent directory, and `-ws` or `--workspaces` to each member of `package.json`'s
`workspaces`. It does not read `pnpm --filter web cs` or `yarn workspace web cs`, nor
`node --run cs`, nor a selector set by `npm_config_workspace` or `.npmrc`, so each
passes though its script runs Biome. Each of the four has one form to use:
`node "$WFC_PLUGIN_ROOT"/scripts/biome-staged.js` plus flags you own, and the rest
in a gate of its own.

The code standards base's §N6 now has a program read whole stdin through
`readFdAll` from `scripts/lib/read-fd.js` and decode the `Buffer`, since a bare
`readFileSync(0)` throws `EAGAIN` on a non-blocking pipe (workflow-core#4017).

The helper surface now lists `readFdAll` from `scripts/lib/read-fd.js` and
`envelope` from `scripts/lib/hook-envelope.js` (workflow-core#4073).

The check refuses no script holding only the `biome-staged.js` command, its root
spelt `"$WFC_PLUGIN_ROOT"` or `"${WFC_PLUGIN_ROOT:-.}"` (workflow-core#4042). It does not read
`npm_config_call='biome check --staged' npx`, which passes though it runs Biome:
declare `node "$WFC_PLUGIN_ROOT"/scripts/biome-staged.js` plus flags you own. It
still refuses text naming the command (`echo "run biome check --staged by hand"
&& eslint .`), so word the text otherwise, and expansions fitting Biome's slots
(`eslint $A $B $C`, `python -m ruff $OPTS check $FILES`), so write the words out;
where it never runs Biome, either may instead go in a shell file
(`sh ./your-gate.sh`).

The check no longer refuses a selector npm answers in part (`npm run x -w web
-w nosuch`, `npm run x -w nosuch -iwr`, `npm run x -ws -iwr` with no workspaces) or
reads as a member (`npm run lint -w "!api"`, `-w @sc/un`) where what it answers runs
no Biome, the part missed being a plain name (workflow-core#4069). It does not read a run made
through `npm exec` or `npx` (`npm exec -- npm run cs`, `npm exec -w web -- npm run
cs`, `npx -w web npm run cs`), nor a member `-ws` reaches only through a symlink past
a glob's segment (`packages/*/sub`) or a `.` in a brace (`{.,web}`), each of which
passes though its script runs Biome: declare `node "$WFC_PLUGIN_ROOT"/scripts/biome-staged.js` plus
flags you own.

Where no split route exists for the refill panel, `scripts/refill-panel-open.js --if-enabled`
now says why on stderr and holds it and the printed command on screen for 5 seconds
before your agents alias starts the view, which otherwise covers them at once (workflow-core#4066).
Stdout is still the command alone, and a
by-hand run without `--if-enabled` prints it and returns at once.

Where a route does exist, `--if-enabled` now runs the routes in a detached process and
returns at once, so your agents view starts without waiting on the split (workflow-core#4080). A
route that fails, and the command to run where all of them fail, go to the refill
loop's log (`.refill-loop.log`) and never on screen, with no hold. A by-hand run still
tries them itself and reports on its own stderr.

`scripts/generate-test-read-edges.js --check` now passes in a repo with no
`docs/test-read-edges.json` in the index or HEAD (workflow-core#4117).

`resolveCore({ root })` and `resolve_core(root=...)` now find the install from a
`root` that is a linked worktree, through its main checkout, rather than throwing
`no workflow-core directory for pin` (workflow-core#4117). So does a main checkout's `root`
spelt through a symlink or with a trailing slash, through git's spelling of it. A
`root` with an install row of its own now resolves without running git, and both
files now fail alike where `git rev-parse` prints fewer than two lines (workflow-core#4150).

`scripts/check-test-spawn.js` now reads a `spawn-kept: <why>` in a file's opening
comments when a shebang stands above them (workflow-core#4117).

Upgrading now adds a `status` script to your `package.json`,
`node scripts/lib/resolve-core.js scripts/status-report.js`, so `npm run status`
runs the plugin's status report and prints your primitives count line (workflow-core#4151).
Nothing is owed. A `status` script you already declare is kept, and a repo with no
`package.json` is given none. The file is laid out as `npm pkg set` writes it.

`scripts/install-refill-boot-unit.js` now also installs and starts a timer that
resumes a refill loop that died with no stop on record at its next firing, within
about 90 s, and the boot unit now starts the loop at `oom_score_adj` 0 (workflow-core#4139).

The code standards base's §X11 House line now states that a `check-*` program whose
body does its own I/O under `runCheck` has no core, so owes no boundary set until a
change gives it one (workflow-core#4138). Nothing is owed.

The code standards base's new §G12 has a Node hook build its `hookSpecificOutput`
or `PostToolUse` decision through `envelope` from `scripts/lib/hook-envelope.js`,
never an object literal of its own, since the harness drops a misspelt event name
or key without an error (workflow-core#4025).

Your pre-commit now runs `scripts/check-program-output.js` on a commit staging a
program under `scripts/` or `.claude/skills/*/scripts/`, refusing any program in
those trees that calls `process.exit` and writes through `console`,
`process.stdout.write` or `process.stderr.write` rather than `writeFd` from
`scripts/lib/write-fd.js`, with no `console-kept: <why>` comment on the line or the
line above (base §N6, workflow-core#4018). A `report-*` honours no such comment, and that
refusal moved here from `scripts/check-report-programs.js`, which now judges only
how a `report-*` files an issue.

`scripts/biome-staged.js` now starts Biome in a main checkout, where it exited 2
with `biome would not start: spawnSync biome ENOENT` (workflow-core#4079). Your pre-commit now
puts the main checkout's `node_modules/.bin` on `PATH` as an absolute path, and
the script resolves any relative `PATH` entry against the directory it was run
from. A wrapper you wrote to give it an
absolute `PATH` can go: declare
`node "$WFC_PLUGIN_ROOT"/scripts/biome-staged.js` plus flags you own as
`commands.check_staged`.
