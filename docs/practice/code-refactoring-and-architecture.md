# code-refactoring-and-architecture

Researched: 2026-10-21

Scope: module boundaries in a Node.js CLI and hook repo that uses a pure decision core and a program shell. Each bullet gives the practice, then the sources, then the evidence rank. "Agree" means three independent sources say the same thing.

## Module boundaries, cohesion and change coupling

- Start the split from a list of design decisions that are difficult or likely to change. Make each module hide one such decision from the other modules. Do not split along the steps of the processing (the "flowchart"). Parnas, "On the Criteria To Be Used in Decomposing Systems into Modules", CACM 15(12), 1972 (free copy: wstomv.win.tue.nl/edu/2ip30/references/criteria_for_modularization.pdf, Conclusion: "it is almost always incorrect to begin the decomposition ... on the basis of a flowchart"); Martin, "The Single Responsibility Principle" (blog.cleancoder.com, 2014-05-08, cites Parnas); Ousterhout and Martin, "A Philosophy of Software Design vs Clean Code" (github.com/johnousterhout/aposd-vs-clean-code, 2024-09 to 2025-02) [named expert]
- Make the interface show as little as possible about the inner work. Parnas 1972 ("Its interface or definition was chosen to reveal as little as possible about its inner workings"); Ousterhout, aposd-vs-clean-code ("deep" methods replace "reading the detailed implementation" with "learning the interface") [named expert]
- A module has one reason to change. A reason to change is one group of people or one business function. Keep together the things that change for the same reasons, and separate the things that change for different reasons. Martin, SRP post 2014 ("Gather together the things that change for the same reasons. Separate those things that change for different reasons."); Parnas 1972 (hide each decision "likely to change"); Beck, as cited by Fowler, "BeckDesignRules" (martinfowler.com/bliki, 2015-03-02: "Once and only Once") [named expert]

- Put the elements that change at the same time in one place, and move out the elements that do not change with them. Beck, "Cohesion" (newsletter.kentbeck.com/p/cohesion, 2022-11-01: "put everything that changes at the same time in one place"; free opening only, rest paywalled and unread) and "Cohesion and elements that aren't" (2022-11-15: "Coupled elements should be sub-elements of the same containing element"; paywalled after the opening); Martin, SRP post 2014; Parnas 1972 [named expert]
- Keep a policy apart from the mechanism that applies it, because policy changes faster than mechanism. Raymond, *The Art of Unix Programming* (2003, free at catb.org/esr/writings/taoup/html/ch01s06.html, Rule of Separation: "policy and mechanism tend to mutate on different timescales, with policy changing much faster than mechanism"); Martin, SRP post 2014 (different reasons to change go in different modules); Parnas 1972 [named expert]
- Use version history to find modules that change together. Such logical coupling is a hidden dependency that static analysis cannot see. Mine it from `git log`, then compare it with the planned module boundaries. Zimmermann, Weissgerber, Diehl, Zeller, "Mining Version Histories to Guide Software Changes", ICSE 2004 (free PDF st.uni-trier.de/diehl/pubs/icse04.pdf; abstract: rules "show up item coupling that is undetectable by program analysis" and "prevent errors due to incomplete changes"; ROSE predicts 26% of further files, top three hold a correct location 64% of the time) [named expert]; Tornhill, code-maat README (github.com/adamtornhill/code-maat, GPL-3.0: "Logical coupling refers to modules that tend to change together"; defaults min-revs 5, min-coupling 30%, max-changeset-size 30) [named expert]; CodeScene docs, "Change Coupling" (docs.enterprise.codescene.io, v4.4 to v6.0: "Change coupling in itself is neither good nor bad ... compare this information to your architectural principles", a vendor's reasoned guidance) [named expert]
- Change coupling correlates with defects better than the Chidamber-Kemerer complexity metrics in three systems. D'Ambros, Lanza, Robbes, "On the Relationship Between Change Coupling and Software Defects", WCRE 2009 (author PDF inf.usi.ch/lanza/Downloads/DAmb2009e.pdf returned 403; claim read only in a search summary of the paper) [unverified]
- Do not count large commits as coupling evidence: a commit that touches many files (a sweep, a re-anchor, a rename) makes every pair look coupled. Filter by change-set size and by a minimum revision count. code-maat README (`--max-changeset-size` default 30, `--min-revs` default 5); CodeScene docs v2.7 (average-revisions filter: "We do not want to consider two files coupled just because they were created in the same commit", a vendor's reasoned guidance) [named expert]

## Pure core, I/O shell and policy tables

- Put the decisions in a pure core that takes values and returns values. Put the reads, writes, process exit and stderr text in a thin shell around it. The shell then has few conditionals, and the core tests need no test doubles. Bernhardt, "Functional Core, Imperative Shell" (destroyallsoftware.com screencast, 2012-07-12, free summary only; video unread) and "Boundaries" (SCNA 2012, free summary only); Seemann, "Impureim sandwich" (blog.ploeh.dk, 2020-03-02: "Gather data from impure sources. Call a pure function with that data. Change state ... based on return value"); Seemann, "Functional architecture is Ports and Adapters" (blog.ploeh.dk, 2016-03-18: a pure function cannot call an impure one, so impure code goes at the edges); Cockburn, "Hexagonal (Ports and Adapters) Architecture" (alistair.cockburn.us, 2005). All four are read in this repo's docs/research/hexagonal-testing.md F1, F2 [named expert]
- Use simple values, not objects with behaviour, as the boundary between the core and the shell. Where a value can replace a port, you need no fake and no contract test. Bernhardt "Boundaries" (summary); Seemann 2020 (the pure function gets data, not a service); docs/research/hexagonal-testing.md F2 (the analysis "where a value can replace a port, no contract test is necessary") [named expert]
- No source measures the effect of this split on run time or defects. Use it for the design reasons above, not for a claimed speed figure. docs/research/hexagonal-testing.md Q1 and Q2 [unverified]
- Put a policy as data (a table), and keep the code that reads the table simple. Choose complex data over complex code. Raymond 2003, Rule of Representation ("Fold knowledge into data, so program logic can be stupid and robust"; "compare an array initializer expressing a conversion table with an equivalent switch statement"); Pike, "Notes on Programming in C" (1989), Rule 5 ("Data dominates", quoted in Raymond 2003); Brooks, *The Mythical Man-Month* (1975, "show me your tables", quoted in Raymond 2003; book itself unread, paywalled). McConnell, *Code Complete* 2nd ed., ch. 18 "Table-Driven Methods" is paywalled and unread [named expert]
- Decide where the table lives from its reason to change, not from its size. A table that changes for its own reason (a ruling, a new rule row) and that more than one program reads goes in its own module, or in the pure core that owns that decision. A table that only one program reads and that changes only with that program stays in that program's pure core. Do not put the table in the I/O shell, because then a test of the policy needs the I/O. Derived from Raymond 2003 (policy apart from mechanism), Martin SRP 2014 (one reason to change), Parnas 1972 (hide the decision likely to change), Bernhardt 2012 (decisions in the core). No single source states this rule for tables in these words, so it sets no default [unverified]

## Deep modules and when to split

- Make modules deep: much behaviour behind a small interface. A shallow module, whose interface is almost as complex as its body, gives little and costs an extra place to read. Ousterhout, aposd-vs-clean-code ("they replace a large cognitive load (reading the detailed implementation) with a much smaller cognitive load (learning the interface). I call these methods 'deep'"; the book *A Philosophy of Software Design* 2nd ed. is paywalled and unread, and the free 2nd-edition extract PDF at web.stanford.edu/~ouster is an image scan that gave no text); Gross, "The Grug Brained Developer" (grugbrain.dev: "good cut point has narrow interface with rest of system: small number of functions or abstractions that hide complexity"); Parnas 1972 (interface reveals "as little as possible"); this repo's .claude/skills/codebase-design/SKILL.md uses the same depth model [named expert]
- Do not split a module so far that two parts become entangled: if you must read part B to understand part A, join them again. Martin and Ousterhout both agree that over-splitting is possible; they disagree only on how far to split. Ousterhout and Martin, aposd-vs-clean-code, Method Length Summary ("We agree that it is possible to over-decompose"; "Entangled methods can usually be improved by combining them so that all the code is in one place"); Metz, "The Wrong Abstraction" (sandimetz.com, 2016-01-20); Gross, grugbrain.dev ("sometimes grug go too early and get abstractions wrong, so grug bias towards waiting") [named expert]
- Do not use a line count as the reason to split. Split when a module changes for two different reasons (Fowler's smell "Divergent Change"); join or move code when one change must touch many modules ("Shotgun Surgery"). Ousterhout, aposd-vs-clean-code ("Setting arbitrary numerical limits ... exacerbates this problem"); Google eng-practices, "Small CLs" ("There are no hard and fast rules about how large is 'too large'"); Fowler and Beck, *Refactoring* (1999, 2nd ed. 2018), smells "Divergent Change" and "Shotgun Surgery" (book paywalled and unread; definitions read in the free summaries at refactoring.guru/smells/shotgun-surgery and a Duke CS308 smells taxonomy PDF); Martin, SRP post 2014 [named expert]
- Wait for real callers before you extract a shared module. Extract on the third similar use (rule of three); before that, duplication is cheaper than a wrong abstraction. When an abstraction is wrong, inline it back into its callers and extract again. Fowler et al., *Refactoring* (1999), rule of three credited to Don Roberts (book unread; cited through en.wikipedia.org/wiki/Rule_of_three_(computer_programming)); Metz 2016 ("duplication is far cheaper than the wrong abstraction"; "the fastest way forward is back"); Fowler, "Yagni" (martinfowler.com/bliki, 2015-05-26: costs of build, delay, carry and repair); Gross, grugbrain.dev ("not factor your application too early") [named expert]
- A second caller alone does not prove that you must extract. Extract when the second caller needs the same decision for the same reason to change. If the two callers will change for different reasons, keep two copies. Derived from Metz 2016, Martin SRP 2014 and the rule of three above. No source gives the "second caller" test in these words, so it sets no default [unverified]

## Refactoring discipline

- A refactoring changes the internal structure and keeps the observable behaviour. Do it as a series of small steps, and keep the tests green after each step. Fowler, "DefinitionOfRefactoring" (martinfowler.com/bliki, 2004-09-01: "without changing its observable behavior"); Fowler, "An example of preparatory refactoring" (martinfowler.com, 2015-01-05: small steps, tests green throughout, "many small changes without going near a debugger"); Gross, grugbrain.dev ("keep refactors relatively small and not be 'too far out from shore'") [named expert]
- Make the change easy, then make the easy change: refactor first into the shape that the new behaviour needs, then add the behaviour. Keep the refactoring and the behaviour change in separate commits or reviews. Beck, quoted in Fowler 2015 ("make the change easy, then make the easy change"); Google eng-practices, "Small CLs" (google.github.io/eng-practices: "It's usually best to do refactorings in a separate CL from feature changes or bug fixes"); Fowler, "Workflows of Refactoring" (2014-01-08, "Two Hats" and "Preparatory Refactoring"; slides only, text not read). Beck, *Tidy First?* (O'Reilly 2023) gives the same split of tidyings from behaviour changes; book paywalled and unread [named expert]
- Have self-testing code before you refactor. Test first, make it pass, then refactor both new and old code. Fowler, "TestDrivenDevelopment" (martinfowler.com/bliki, 2005-03-05, updated 2023-12-11: refactoring is "a key part of the process", and skipping it is the most common way to get TDD wrong); Fowler, "Yagni" 2015 (refactoring and self-testing code make yagni viable); Ousterhout and Martin, aposd-vs-clean-code, TDD Summary ("We agree that unit tests are an essential element"; they disagree on test-first against tests written in bundles after the code) [named expert]
- Effort to make code easier to change is not speculative work; a feature or an option built for a need that nobody has confirmed is speculative work. Fowler, "Yagni" 2015 (yagni "does not apply to effort to make the software easier to modify"); Beck design rules (Fowler bliki 2015: "Fewest elements"; elements added for future flexibility often made systems harder to modify); Metz 2016 [named expert]
- A code smell is a hint, not a rule: check that a real problem is under it before you refactor. Fowler, "CodeSmell" (martinfowler.com/bliki, 2006-02-09: "smells don't always indicate a problem"); Ousterhout and Martin, aposd-vs-clean-code (over-decomposition is a real failure); Metz 2016 [named expert]
- The field body of knowledge lists the same core design principles: abstraction, coupling, cohesion, decomposition and modularization, encapsulation and information hiding, and separation of interface and implementation. IEEE Computer Society, SWEBOK V4 (2024), ch. 3 "Software Design" (behind a free signup; not read directly, only through the course notes that follow) [standard or field body]; University of Edinburgh, Inf2-SEPP 2026 lecture 9 part 1 (opencourse.inf.ed.ac.uk, points to SWEBOK V4 ch. 3; "Low or loose coupling is desirable"; "High cohesion is desirable") [named expert]

## Naming functions

- Name a function with a verb or verb phrase saying what it does, and keep noun phrases for values. Google JavaScript Style Guide §6.2.3 (google.github.io/styleguide/jsguide.html: "Method names are typically verbs or verb phrases"); Cwalina and Abrams, *Framework Design Guidelines* 2nd ed., reprinted at learn.microsoft.com, "Names of Type Members" ("DO give methods names that are verbs or verb phrases", which "serves to distinguish method names from property and type names, which are noun or adjective phrases"); Kotlin coding conventions, "Choose good names" (kotlinlang.org/docs/coding-conventions.html: "The name of a method is usually a verb or a verb phrase saying what the method does") [named expert]. PEP 8 sets no verb rule for Python, only lowercase with underscores [standard or field body]

## Tools practitioners use

- dependency-cruiser: checks the import graph against rules in a config file (`forbidden`, `allowed`, `required`, `circular`, `orphan`, `dependencyTypes`). A rule can make a boundary a check, for example "a pure core must not import `node:fs` or `node:child_process`", "no import cycles", "no orphan modules". MIT, v18.7.0, read 2026-10-25, about 3.3M npm downloads a week. github.com/sverweij/dependency-cruiser doc/rules-reference.md [standard or field body]. Only its own docs vouch, so it sets no default to use it
- madge: draws the module graph and lists circular dependencies (`.circular()`); it has no rule engine. MIT, v8.0.0, read 2026-10-25, about 1.6M downloads a week. github.com/pahen/madge README [standard or field body]. Only its own docs vouch, so it sets no default to use it
- knip: finds unused files, exports and dependencies. ISC, v6.43.0, read 2026-10-25, about 10.9M downloads a week. Ships an MCP server, `@knip/mcp` (v0.0.36, about 3k downloads a week), that "enables coding agents to configure Knip automatically" (knip.dev/reference/integrations); no agent skill. The MCP server is Claude-compatible but young; per the house rule it needs a proposal ticket before install [standard or field body]. Only its own docs vouch, so it sets no default to use it
- eslint-plugin-boundaries: ESLint rules for allowed imports between element types (MIT, v7.3.0, read 2026-10-25, about 1.1M downloads a week). It fits only where a repo already lints its scripts with ESLint. npmjs.com/package/eslint-plugin-boundaries [standard or field body]. Only its own docs vouch, so it sets no default to use it
- jscpd: finds copy-pasted code (MIT, v5.4.2, read 2026-10-25, about 2.1M downloads a week). npmjs.com/package/jscpd [standard or field body]. Only its own docs vouch, so it sets no default to use it
- code-maat (Tornhill, GPL-3.0, Java jar, v1.0.4, read 2026-10-26) and CodeScene (commercial and hosted, docs read up to v6.0 on 2026-10-21) mine change coupling from `git log --numstat`. For a small repo, a short script over `git log --name-only` with change-set-size and min-revs filters gives the same pair counts and needs no new dependency. code-maat README; CodeScene docs, each on how its own tool mines coupling [standard or field body]. That the short script matches them is this note's own reading of their filters, which no source states, so it sets no default [unverified]
- Claude-compatible options found in the Claude plugin directory cache (2026-10-21): `typescript-lsp` 1.0.0 and `serena` (anthropics/claude-plugins-official; the marketplace entry is unversioned, upstream oraios/serena is v2.1.0) give find-references and symbol navigation, which help with move and rename refactors; `code-simplifier` 1.0.0 and `pr-review-toolkit` (same marketplace, unversioned; installed here) review simplification. Versions read 2026-10-26 at marketplace commit 5826794 (2026-10-23). No plugin or MCP server for dependency-cruiser, madge or change coupling was found.
