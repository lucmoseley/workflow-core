# crash-and-os-incident-diagnosis

Researched: 2026-11-12

## Capturing evidence

- A small (mini) dump holds only the thread that stopped, so it can miss a cause outside that thread; set a kernel dump or larger before the next crash. Microsoft Learn, "Memory dump file options", learn.microsoft.com/en-us/troubleshoot/windows-server/performance/memory-dump-file-options ("errors that were not directly caused by the thread that was running … may not be discovered") [standard or field body]
- Which larger type Microsoft's own pages disagree on: Windows Server's best-practices page sets a complete dump (0x1) with a page file of RAM + 300 MB at 32 GB of RAM or less, and an automatic dump (0x7) with a system-managed page file above; Windows Client's stop-code page says automatic for every size but asks for a complete dump in its debugging steps. learn.microsoft.com/en-us/troubleshoot/windows-server/performance/troubleshoot-stop-errors-best-practices-dump-configuration-recommendations; learn.microsoft.com/en-us/troubleshoot/windows-client/performance/stop-code-error-troubleshooting [standard or field body]. The common floor is kernel or larger; a complete or active dump also holds user-mode memory, such as WSL2's VM process.
- An automatic dump grows the page file to at least the size of RAM, for 4 weeks, only after a crash whose kernel dump did not fit. Microsoft Learn, "Automatic Memory Dump", learn.microsoft.com/en-us/windows-hardware/drivers/debugger/automatic-memory-dump [standard or field body]. So the first crash after a page-file shrink can leave a small dump or none: an inference, which sets no default [unverified].
- A firmware recovery watchdog (ASR) can power-reset the host while the dump is being written, leaving none. Best-practices page above ("This behavior interrupts the dump process") [standard or field body]
- Where a reset left no dump, look in `%SystemRoot%\LiveKernelReports`: live dumps are written without a reset, and watchdog live dumps catch "failure paths that were not anticipated". Microsoft Learn, "Kernel Live Dump Code Reference", learn.microsoft.com/en-us/windows-hardware/drivers/debugger/kernel-live-dump-code-reference [standard or field body]. On an SoC host, bug check 0x175 (PREVIOUS_FATAL_ABNORMAL_RESET_ERROR) reports a past reset, a hardware watchdog among its causes. learn.microsoft.com/en-us/windows-hardware/drivers/debugger/bug-check-0x175--previous-fatal-abnormal-reset-error [standard or field body]
- Prove the dump path with a forced crash before relying on it. Sysinternals NotMyFault, learn.microsoft.com/en-us/sysinternals/downloads/notmyfault (what the tool does) [standard or field body]; Microsoft's dump-configuration pages above ask for the same test [standard or field body]. NotMyFault on ARM64 is not stated [unverified].
- Plan the capture path before the crash, and read the boot before the reset. Linux does the same with kdump (docs.kernel.org/admin-guide/kdump/kdump.html), pstore/ramoops (docs.kernel.org/admin-guide/ramoops.html) and `journalctl -b -1` (freedesktop.org/software/systemd/man/latest/journalctl.html): one more adopter, setting no default of its own [unverified]. WSL's `debugConsoleLogFile` writes the guest kernel's console to a Windows file. learn.microsoft.com/en-us/windows/wsl/wsl-config [standard or field body]

## Dump analysis

- Run `!analyze -v` with Microsoft's public symbol server on the path, and treat the module it names as a lead, not a verdict: it is "the first frame whose owner is found in this search". Microsoft Learn, "Using the !analyze Extension", learn.microsoft.com/en-us/windows-hardware/drivers/debugger/using-the--analyze-extension [standard or field body]
- A core-OS (`nt!`) frame is often the victim of corruption made elsewhere. Microsoft's stop-code page: about 70% of crashes come from third-party drivers, 10% from hardware, 5% from Microsoft code and 15% are unknown [named expert]; NTDebugging, "A Classic Case of Whodunit", learn.microsoft.com/en-us/archive/blogs/ntdebugging/a-classic-case-of-whodunit (an `nt!` crash fixed by replacing the processor) [named expert]
- Check the hardware did what the code asked: compare the faulting address in the bug-check parameters or fault register with the address the instruction computed; a one-bit difference points to hardware, as do `!analyze`'s SINGLE_BIT_ERROR and TWO_BIT_ERROR fields. Its CHKIMG_EXTENSION field marks memory corruption, which software causes too. NTDebugging, "Hardware bitflipping", learn.microsoft.com/en-us/archive/blogs/ntdebugging/hardware-bitflipping [named expert]; the `!analyze` page above for the fields [standard or field body]. The ARM64 register (FAR_EL1) mapping is [unverified].
- Read each bug check's parameters from its own page before reading the stack; for 0xBE, parameter 1 is the address written and parameter 2 the PTE contents. learn.microsoft.com/en-us/windows-hardware/drivers/debugger/bug-check-0xbe--attempted-write-to-readonly-memory [standard or field body]
- Run Driver Verifier on suspect drivers only, in groups of 10–20 and never all at once, special pool on one driver at a time, and clear it with `verifier /reset`. Stop-code page above ("Don't try to verify all the drivers at one time") [standard or field body]. Microsoft's driver-test page says to run it only on test computers (learn.microsoft.com/en-us/windows-hardware/drivers/devtest/driver-verifier) while its support page applies it to the crashing machine; on a machine that is not a test box, weigh that before turning it on [standard or field body].

## Event-log forensics

- Read Kernel-Power 41 by its fields: a non-zero BugcheckCode (decimal) is a stop error, a non-zero PowerButtonTimestamp a forced power-off, and all zeros means Windows recorded no cause, typically power or other hardware. Microsoft Learn, "Event ID 41", learn.microsoft.com/en-us/troubleshoot/windows-client/performance/event-id-41-restart [standard or field body]
- Before calling a reset "no bug check", look for volmgr event 46 ("Crash dump initialization failed!") and check the page file. Event ID 41 page above [standard or field body]
- Read the events as one set — 41, 6008 (time of the dirty shutdown), 1001 BugCheck (code, parameters, dump path), 1074 and 6006 — and fix the time zone of any exported `.evtx` first. Event ID 41 page and best-practices page above [standard or field body]
- No WHEA event does not mean healthy hardware: WHEA reports only errors the hardware detects and the firmware describes. Microsoft Learn, "Hardware Errors and Error Sources", learn.microsoft.com/en-us/windows-hardware/drivers/whea/hardware-errors-and-error-sources [standard or field body]. Consumer machines mostly lack ECC (Nightingale, Douceur and Orgovan, "Cycles, Cells and Platters", EuroSys 2011, microsoft.com/en-us/research/wp-content/uploads/2016/02/eurosys84-nightingale.pdf [named expert]), so a DRAM bit flip there can show as a crash with no event: derived [unverified]. Whether a given SoC reports memory errors to WHEA is [unverified] until checked on that platform.
- Kernel-Power 142 records that "the system stopped responding and the hardware watchdog triggered a system reset". Kernel-Power 109 (the kernel began a shutdown), 105 (power source change), 172 (standby connectivity) and 506/507 (entering and leaving Modern Standby) record ordinary transitions and prove no fault. The Kernel-Power provider manifest, read with `wevtutil gp Microsoft-Windows-Kernel-Power /ge /gm:true /f:xml` on build 10.0.26200 [standard or field body]; one vendor source, as no web page defines 142. That it shows a hang a bare 41 cannot, reading a 109 just before a reset as a shutdown Windows began, or a 506 with no 507 as a reset during standby, is inference and sets no default [unverified].
- Start from what changed just before the first crash: Reliability Monitor (`perfmon /rel`) lists installs and updates beside failures. Microsoft Ask the Performance Team, techcommunity.microsoft.com/blog/askperf/using-reliability-monitor-for-troubleshooting/372962 (what the tool records) [standard or field body]; Google SRE book, "Effective Troubleshooting", sre.google/sre-book/effective-troubleshooting/ ("Recent changes to a system can be a productive place to start") [named expert]

## Hardware or software

- Suspect a driver first, and turn to hardware when a dump shows an impossible result. Chen, "There's an awful lot of overclocking out there", devblogs.microsoft.com/oldnewthing/20050412-47/?p=35923 [named expert]; the stop-code page's shares above [named expert]. A stack that differs in every dump is not proof of hardware: memory corruption by software does the same (NTDebugging, "Whodunit", above) [named expert].
- Remove overclocking and undervolting, check cooling, and update firmware, Windows and drivers before deeper work. Bug Check 0x124, learn.microsoft.com/en-us/windows-hardware/drivers/debugger/bug-check-0x124---whea-uncorrectable-error, and the stop-code page [standard or field body]; Nightingale ("underclocked machines are significantly more reliable") [named expert]
- Test memory outside the running OS. Memtest86+ v9 runs on ARM64, tested on a Snapdragon X laptop, and is not Microsoft-signed, so Secure Boot needs its CA enrolled or must be off. memtest.org (what the tool does) [standard or field body]; the default to test memory rests on the stop-code page ("Run any relevant hardware and memory tests") and the Event ID 41 page's check list ("Check the memory") [standard or field body]. No source sets a number of passes, so none is set.
- Under WSL2 the host OS is the Hyper-V root partition, "the only partition that has direct access to physical memory and devices". Microsoft Learn, "Hyper-V Architecture", learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/architecture [standard or field body]. A hypervisor fault shows as bug check 0x20001 (HYPERVISOR_ERROR; learn.microsoft.com/windows-hardware/drivers/debugger/bug-check-0x20001--hypervisor-error, unread beyond a search result) [unverified]. That a guest's memory load reaches the host's memory manager is an inference [unverified].
- A feature that toggles alone, such as memory page combining (`Disable-MMAgent -PageCombining`, learn.microsoft.com/en-us/powershell/module/mmagent/enable-mmagent [standard or field body]), makes a clean one-variable test; turning off the frame a dump names can hide a victim symptom and leave the cause, so judge it by the crash rate after, not by the absence of that one stack [unverified]; this sets no default.

## Hangs, watchdogs and traces

- A frozen machine that never bug-checks can be made to dump from the keyboard: `CrashOnCtrlScroll`=1 under `HKLM\SYSTEM\CurrentControlSet\Services\kbdhid\Parameters` (`i8042prt` for PS/2, `hyperkbd` for Hyper-V), restart, then right Ctrl + Scroll Lock twice gives bug check 0xE2; `Dump1Keys`/`Dump2Key` set another pair for a keyboard with no Scroll Lock. It fails on a hang at high IRQL. Microsoft Learn, "Forcing a system crash from the keyboard", learn.microsoft.com/en-us/windows-hardware/drivers/debugger/forcing-a-system-crash-from-the-keyboard; "Windows-based computer freeze troubleshooting", learn.microsoft.com/en-us/troubleshoot/windows-client/performance/windows-based-computer-freeze-troubleshooting [standard or field body]
- Since Windows 8 an NMI always bug-checks with 0x80, "not configurable", so `NMICrashDump` is no longer needed. learn.microsoft.com/en-us/troubleshoot/windows-client/performance/nmi-hardware-failure-error [standard or field body]
- Watchdog live dumps land in `%SystemRoot%\LiveKernelReports\WATCHDOG` without a reset, and are throttled. Kernel Live Dump Code Reference, above [standard or field body]; OSR, "Live Kernel Reports", osr.com/nt-insider/2019-issue1/live-kernel-reports/ ("CheckPolicy throttled dump creation") [named expert]. So finding none does not prove there was no stall: derived [unverified].
- A hardware watchdog resets the machine when the OS stops restarting its count, and keeps a "Watchdog Fired" bit so the next boot can tell its reset from others; firmware describes it in the ACPI WDRT table. Microsoft Learn, "Watchdog timer hardware requirements for Windows", learn.microsoft.com/en-us/previous-versions/windows/hardware/design/dn614007(v=vs.85), archived, server-era [standard or field body]. Unread: Microsoft's WDAT specification.
- Snapdragon SoCs carry an OS-owned and a TEE-owned watchdog; on Qualcomm Linux the TEE one bites at 22 s and the PMIC then resets the whole system. Qualcomm Linux Debug Guide 80-80022-12, docs.qualcomm.com/bundle/publicresource/80-80022-12/topics/general_system_debugging.md [standard or field body], for Qualcomm Linux only. No free source gives the Windows-on-Snapdragon values, so that a long hang there ends in a reset with no dump, leaving 142 or 0x175 as the evidence, is inference and sets no default [unverified].
- A dump is one instant; a trace records how the machine got there, and has found a stall no dump could show. Microsoft escalation engineer, "Another case of unexplained server hang: ETW to the rescue", learn.microsoft.com/en-us/archive/blogs/davguents_blog/another-case-of-unexplained-server-hang-etw-to-the-rescue ("a kernel dump is a representation of a single point of time not a recorder") [named expert]. One expert, so it sets no default to trace before dumping.
- WPR's default memory mode is a circular buffer in RAM, which Microsoft recommends sizing at 1–5% of RAM, that ETW does not flush on its own, so a hard reset most likely loses it (inference) [unverified]. To keep a trace through a sudden reset, log to a circular file with a non-zero FlushTimer ("if you want to be sure to get events even if the system crashes"), or put ETW buffers into the dump with `EVENT_TRACE_ADDTO_TRIAGE_DUMP`; `!wmitrace.logdump` recovers WPP and legacy ETW buffers from a dump. Microsoft Learn, "Logging Mode" (learn.microsoft.com/en-us/windows-hardware/test/wpt/logging-mode), "Logging Mode Constants" (learn.microsoft.com/en-us/windows/win32/etw/logging-mode-constants), EVENT_TRACE_PROPERTIES (learn.microsoft.com/en-us/windows/win32/api/evntrace/ns-evntrace-event_trace_properties), `!wmitrace.logdump` (learn.microsoft.com/en-us/windows-hardware/drivers/debuggercmds/-wmitrace-logdump) [standard or field body]. That `wpr -boottrace` covers only boot and shutdown is read from the WPR command-line options (learn.microsoft.com/en-us/windows-hardware/test/wpt/wpr-command-line-options) by inference, and sets no default [unverified].
- Read a WSL2 VM's death from the Windows side: the WSL trace (`wpr -start wsl.wprp -filemode`) carries the guest's dmesg as `GuestLog` events, and `debugConsole`/`debugConsoleLogFile` capture its console; `wsl --debug-shell` works only while the VM runs. microsoft/WSL `doc/docs/debugging.md` [standard or field body]

## Repeated incidents

- Expect a hardware fault to recur: a machine that crashed once from a hardware fault is up to two orders of magnitude likelier to crash again; after a one-bit DRAM failure, 94% of second crashes come within 10 days, and DRAM failures recur at the same location. Nightingale, above [named expert]; Chen, devblogs.microsoft.com/oldnewthing/20141226-00/?p=43293 ("you have to get lightning to strike twice") [named expert]
- Keep every incident in one table — time, uptime, load, code and parameters, top frames, named module — and read it for consistency. Stop-code page ("consistent across all instances of the crash") [standard or field body]. Varying stacks most often mean memory corruption by software, but hardware faults can repeat one stack, so consistency alone does not split them. NTDebugging, "Whodunit", above [named expert]; SRE book ("correlation is not causation"; "Take clear notes") [named expert]
- One dump settles a cause only when it is self-consistent: a named third-party driver with a matching stack, or a WHEA record. It does not settle corruption, a core-OS victim, or resets that left no dump, and it never shows that dumpless resets share its cause. Stop-code page ("If you can replicate the problem, you can usually determine the cause") [standard or field body]; Whodunit above [named expert]
- Change one variable at a time, falling back to the default configuration, and rule a cause out with a soak sized from the crash rate. SRE book ("change the system in a controlled way") [named expert]; Event ID 41 page [standard or field body]. Size the soak by `docs/practice/measurement-and-experiment-design.md` (zero events in n days bounds the rate below 3/n at 95%; NIST e-Handbook §8.3.1.1) [standard or field body]. Hardware recurrences cluster in time (84% of machines recur within 10 days; Nightingale [named expert]), so a short soak is weaker evidence than 3/n implies [unverified]; the research pass's "about 30 days" is derived, not sourced, and sets no default [unverified].
