# project-and-roadmap-management

Researched: 2026-10-24

Scope: breaking a spec into tickets that can each be built and landed, ordering the ready tickets, and reviewing the ticket mix and the process changes a retro makes, in a repo where many agent sessions work at once. Each bullet gives the practice, then the sources, then the evidence rank.

## Breaking a spec into tickets

### Vertical (tracer-bullet) slices

- Cut each ticket as a vertical slice: one narrow path through every layer the behaviour touches, with its tests, that you can demo or check on its own. Do not cut one ticket per layer. Wake, "INVEST in Good Stories, and SMART Tasks" (xp123.com, 2003-08-17: "slice vertically through the layers"); Lawrence and Green, "The Humanizing Work Guide to Splitting User Stories" (humanizingwork.com: a vertical slice is "a work item that delivers a valuable change in system behavior"; layer splits may meet "small" but fail "independent and valuable"); Singer, *Shape Up* ch. 11 "Get One Piece Done" (basecamp.com/shapeup, free: "integrating vertically on one small piece of the project instead of chipping away at the horizontal layers"); Google eng-practices, "Small CLs" (google.github.io/eng-practices: "Splitting Vertically" into "small, full-stack features") [named expert]
- Make the first slice a tracer bullet: the thinnest end-to-end path, kept and grown one feature at a time. A prototype is thrown away; a tracer bullet is not. Venners, "Tracer Bullets and Prototypes", interview with Hunt and Thomas (artima.com, 2003-04-21: "one thin line of execution goes end to end"; "Prototypes are designed to be thrown away"); *Shape Up* ch. 11 (something "tangible and demoable early—in the first week or so"); Pocock, `to-tickets` skill (github.com/mattpocock/skills, skills/engineering/to-tickets/SKILL.md, MIT: each slice cuts "a narrow but COMPLETE path through every layer" and is "demoable or verifiable on its own") [named expert]
- Do any prefactoring first, in its own ticket or change, so that the slices after it are easy. Pocock, `to-tickets` ("Any prefactoring should be done first"; "Make the change easy, then make the easy change", which is Beck's line); Google eng-practices, "Small CLs" ("do refactorings in a separate CL from feature changes or bug fixes"); docs/practice/code-refactoring-and-architecture.md §Refactoring discipline (Beck, Fowler) [named expert]
- Use a time-boxed spike only when no other split removes the uncertainty. A spike's code is thrown away. Lawrence and Green ("make every effort to use one of the previous eight patterns before resorting to the spike pattern"); Venners 2003 (a prototype is for learning and is thrown away) [named expert]

### Sizing a slice

- Size a slice so that it lands and is checked in hours to a couple of days. A slice that takes more than a week to complete and check is too big. As a review-size guide, about 100 changed lines is reasonable and 1000 is usually too many. Do not regroup small slices into one change before testing. DORA, "Working in small batches" (dora.dev/capabilities: "hours to a couple days"; "Any batch of code that takes longer than a week to complete and check is too big"; regrouping "delays the feedback on whether the changes have defects"); Google eng-practices, "Small CLs" ("one self-contained change"; "100 lines is usually a reasonable size", "1000 lines is usually too large"); Lawrence and Green (6 to 10 stories should fit in one iteration); Wake 2003 ("Small", with "at most a few person-weeks" as the upper bound) [named expert]
- For agent work, also size each slice to fit one fresh context window, so that one session can take the slice from start to finish. Pocock, `to-tickets` ("sized to fit in a single fresh context window"). Only one source states this rule and sets no default by itself [named expert]

### Blocking edges

- Give each ticket only the blocking edges that really gate it: ticket A blocks ticket B only when B cannot start or cannot land green without A. Aim for independent tickets. Work the frontier, which is every ticket whose blockers are all done. Wake 2003 ("Stories are easiest to work with if they are independent", which is not always possible); Lawrence and Green (after a split, the stories "still aren't independent, but the dependency is much clearer"); Pocock, `to-tickets` ("does each ticket only depend on tickets that genuinely gate it?"; "Work the frontier: any ticket whose blockers are all done") [named expert]
- Record an edge with the tracker's own blocking link, not in prose, so that boards and `gh issue view` show it. GitHub Docs, "Creating issue dependencies" ("blocked by, or blocking"; a "Blocked" icon on boards; `gh issue view` shows "Blocked by" and "Blocking" rows), which covers what GitHub does only [standard or field body]; Pocock, `to-tickets` ("Use the platform's native blocking relationship where it has one") [named expert]

### Wide refactors: expand, migrate, contract

- A wide refactor is one mechanical change that fans out over many call sites, so no single vertical slice can land green. It is the exception to vertical slicing. Sequence it as a parallel change. Expand: add the new form beside the old one, so nothing breaks. Migrate: move the call sites over step by step, with each step independently committable, tested and green, because the old form still exists. Contract: delete the old form only once no caller remains. Sato, "ParallelChange" (martinfowler.com/bliki, 2014-05-13: "augment the interface to support both the old and the new versions"; migration "can be done incrementally"; remove the old version "once all usages have been migrated"); Fowler, "BranchByAbstraction" (martinfowler.com/bliki, 2014-01-07: move clients section by section; "Ensure that the system builds and runs correctly at all times"; delete the old supplier "once [it] isn't needed"); Winters, Manshreck and Wright (eds), *Software Engineering at Google* ch. 22 "Large-Scale Changes" (abseil.io/resources/swe-book, free: "individual shards should be committable independently", each shard tested in CI); Cartwright, Horn and Lewis, "Patterns of Legacy Displacement" (martinfowler.com, 2024-03-05: transitional architecture is software "we intend to remove when the displacement is complete") [named expert]
- Cut the migrate batches along ownership or module lines: per project, package, directory or family of callers that change together. Give each batch its own ticket, blocked only by the expand ticket, and limit how many batches are open at once. The contract ticket is blocked by every migrate batch. *Software Engineering at Google* ch. 22 (Rosie shards "based upon project boundaries and ownership rules" and "caps the number of outstanding shards for any given LSC"); Pocock, `to-tickets` (batches "sized by blast radius (per package, per directory), each batch its own ticket blocked by the expand"; contract "blocked by every migrate batch"); Fowler, "BranchByAbstraction" (the supplier can be split into sub-components, each moved on its own) [named expert]
- Stop backsliding: once the migration starts, add a check that refuses new callers of the old form, so the contract does not slip. *Software Engineering at Google* ch. 22 ("it's important to have a system that prevents additional introductions of the symbol or system ... an effective method to prevent backsliding"). Only one source states this rule, but Google states it for almost every change of this kind, so it is the default for a repo that has pre-commit gates [named expert]

### Gating a programme of ports by measurement

No source found covers gating a refactoring programme by measurement. The defaults below come from the nearest analogues, staged rollouts and controlled experiments, which make the same promise: carry on only while a measured change stays inside a bound.

- Fix the metric and its acceptable bound before the first batch runs, not after you see the numbers. Use a few metrics (at most a dozen) that reflect what users see, and a stop rule that says what result pauses or reverses the programme. Kohavi, Henne and Sommerfield, "Practical Guide to Controlled Experiments on the Web", KDD 2007 (author copy cdn.elezea.com/pdf/GuideControlledExperiments.pdf, §5.3.1 "Agree on the OEC Upfront": agree "how an experiment is to be evaluated before the experiment is run"; deciding in advance avoids "finding what appear to be significant results by chance"); Google, *The Site Reliability Workbook*, "Canarying Releases" (sre.google/workbook: "no more than a dozen" metrics; "define a notion of acceptable behavior for each of the metrics"; when the canary is worse, "pause and roll back") [named expert]
- Compare each batch against a control measured at the same time, not against a baseline taken earlier. In a parallel change the old form still exists, so it can be the control in the same run. SRE Workbook, "Canarying Releases" (a before/after process is risky because time-driven changes add noise); Cartwright, Horn and Lewis 2024 (parallel run, and dark launching to "Call a new back end feature without using results in order to assess its performance impact"); Fowler, "BranchByAbstraction" (run the new supplier and "compare its behavior with the old one") [named expert]
- Stage the programme: make the first batch small and use it to check the measurement itself, then grow the batch size only after a stage passes. SRE Workbook, "Canarying Releases" ("a canary containing multiple stages"; once a stage passes, "the next stage will have a larger canary population"); Fowler, "StranglerFigApplication" (martinfowler.com/bliki, 2024-08-22: "make both investment and returns occur gradually and visibly") [named expert]
- Decide in the plan what happens to the transitional state if the stop rule fires partway, because the contract step cannot run then. None of the sources read says how to end a parallel change that stops partway. So this entry sets no default [unverified]

## Ordering the frontier toward a target

- When parallel workers take ready tickets from a dependency graph, rank first by the longest path from the ticket to the target (critical path, "highest level first"), not by how many tickets it unblocks. Longest-path-first is optimal for an in-tree of unit tasks on any number of workers, which is the shape of one target and its prerequisites (Hu 1961, through the survey). Kwok and Ahmad, "Static scheduling algorithms for allocating directed task graphs to multiprocessors", ACM Computing Surveys 31(4), 1999, a survey (author copy: descending b-level "tends to schedule critical path nodes first"; reporting Adam, Chandy and Dickson 1974, whose "strong evidence" showed "the CP (critical path) based algorithms have near-optimal performance") [survey or curated list]; Kolisch, Kiel Manuskript 344, 1994 (econstor, free: "LST >- LFT >> MTS", the critical-path rules 5.06% and 5.32% from optimum against 6.65% for most total successors) [named expert]
- Break a tie in path length on successor count. CP/MISF is HLFET with ties going to more immediate successors, the survey's "major improvement"; Kolisch ranks most total successors third of six, good as a secondary key. Kwok and Ahmad 1999 [survey or curated list]; Kolisch 1994 [named expert]. This repo breaks the tie on transitive reach, not immediate successors (mantahostels#101)
- Give a prerequisite the highest priority of everything it holds up, transitively. Sha, Rajkumar and Lehoczky, "Priority inheritance protocols", IEEE Trans. Computers 39(9), 1990 (a blocker "executes its critical section at the highest priority level of all the jobs it blocks"; "Priority inheritance is transitive") [named expert], which covers locks, not precedence edges; for precedence graphs, deadline modification passes a successor's deadline back to its predecessors in one backward pass (Chetto, Silly and Bouchentouf 1990, after Lawler 1973, read only through course slides; the paper is paywalled) [unverified]
- Rank the inherited tier above path length, so a long chain to nothing urgent stays below urgent work. This follows from the two entries above and no source states it alone. This repo adds one more rule: a parent that only closes when its children close adds nothing to the path length, because it holds no work of its own (mantahostels#105 rule 5)

## Reviewing the ticket mix and judging process changes

Researched: 2026-11-08 for this section.

### Reading the ticket mix

- Classify each ticket when it is filed, on a small set of fixed-meaning classes that do not overlap: what the fix changes, and whether earlier work caused the demand. ODC's defect type is "the meaning of the fix", its classes semantic and orthogonal, which "reduces the human error in classification". Seddon's failure demand, "demand caused by a failure to do something or do something right", is one yes/no axis on each unit of incoming work. SRE's outage tracker uses free-form namespaced tags (`cause:`, `action:`) grown from the team's own use. Chillarege et al., "Orthogonal Defect Classification", IEEE TSE 18(11), 1992 (chillarege.com, free) [named expert]; Open University OpenLearn, "Capacity and demand management" [named expert]; Google SRE Book ch. 16 "Tracking Outages" [named expert]
- Read the mix weekly against the team's own baseline, and review the review process monthly. SRE Workbook ch. 10 "Postmortem Culture" (weekly outage report of the last seven days; a monthly cross-functional review of the postmortem process) [named expert]; SRE Book ch. 16 [named expert]
- Act only on a signal across weeks, never on one item or one week. On an XmR chart, the limits are the mean ± 2.66 × the average moving range. A signal is one point outside the limits, or a run of 7 on one side of the mean. Recalculate the limits only after a named process change has held. NHS England, "Making data count: strengthening your decisions", 2019 [standard or field body]; NHS QSIR "Statistical Process Control" guide [standard or field body]. ODC and SRE give no number and judge against experience and the team's own past. Before about 20 weekly points exist, read trend direction only, as ODC does before calibration (Chillarege 1992) [named expert]
- Use counts to find where to look, then read the cases. A count says nothing about severity or difficulty. Nash and Campbell, "Analyzing incident data" (InfoQ, VOID) [named expert]; SRE Book ch. 16 [named expert]. Before filing action items, review similar past incidents and their action items ("incidents that rhyme"). Lunney, Lueder and Beyer, "Postmortem Action Items: Plan the Work and Work the Plan", ;login: Spring 2017 [named expert]
- Group tickets by subject on the title, then confirm a group by reading bodies. Duplicate detection scores best with the title weighted above the description. Borg et al., ESEM 2014 [named expert]; Andrade et al., arXiv:2503.00660, 2025 [named expert]; Ji et al., iPACK, ICSE 2023 [named expert].
- Assign each ticket to a kept list of kinds, in batches, and add a kind only when none fits. Open LLM clustering scores ARI 0.13–0.17 on real data and collapses in one prompt near 1,000 items; assignment to fixed labels reaches F1 about 0.8. Chirkova et al., arXiv:2506.09147, 2025 [named expert]; Aracena et al., ICPC 2025 [named expert]; Colavito et al., MSR 2024, abstract only [named expert]. Count script-made title templates with variable parts masked, as Drain does. iPACK [named expert]
- For a kind's weekly count, flag a point over the c-chart limit, mean + 3 × √mean, and a trend only at 6 points in a row; keep a count floor on every trigger. NIST/SEMATECH e-Handbook §6.3.2 and §6.3.3.1 [standard or field body]. Rank kinds by count as well: a large steady kind trips no change rule. Juran, "The Non-Pareto Principle; Mea Culpa", 1974 [named expert]; Juran Institute, "The Juran Trilogy" [named expert]
- Search the whole tracker, open and closed, before filing: a time window does not help, and a closed issue covering the kind means its fix did not hold, so reopen it or file a follow-up. Borg et al. 2014 [named expert]; Rakha et al. 2018 [named expert]. No source gives a number for a repeat-incident floor or a cap on tickets per review

### Judging whether a process change worked

- Write the prediction, the measure and the success criteria before the change lands. IHI QI Essentials Toolkit, PDSA Worksheet ("make a prediction about what you think will happen"; Act: "Adapt…, adopt…, or abandon") [standard or field body]; SRE Workbook ch. 10 (each action item has "a verifiable end state") [named expert]; Lean Enterprise Institute lexicon, "PDCA" [standard or field body]
- Decide on a fast process (mechanism) measure. Watch the slow outcome measure as a trend only, and add a balancing measure to catch harm elsewhere. IHI "Model for Improvement" and its family of measures [standard or field body]; NHS Wales Improvement Cymru, "Family of measures" [standard or field body]; DORA, "The four keys" guide (leading indicators; several metrics that pull against each other) [named expert]
- Let the measure set the review interval, not the calendar: as short as the process measure can show a change. No source fixes a number of days. IHI PDSA [standard or field body]; NHS "Making data count" [standard or field body]
- When the evidence is inconclusive, the change does not become the standard. Revert a cheap change, or run one sharper test. LEI: "standardize and stabilize the change or begin the cycle again, depending on the results" [standard or field body]; IHI (adapt, not adopt) [standard or field body]. Do not adjust a stable process on one result: Deming's funnel experiment shows tampering widens the spread. The W. Edwards Deming Institute, "Impact of Process Tampering on Variation" [named expert]
- Judge a change against a multi-week baseline and a control series, never against the extreme week that triggered it, or regression to the mean reads as a gain. Start each change on one known date. Campbell, "Assessing the Impact of Planned Social Change", 1976 (free reprint, JMDE 7(15), 2011: effects of programs started "in response to an acute problem" are "confounded with 'regression artifacts'"; "Gradually introduced changes are usually impossible to detect") [named expert]; Barnett, van der Pols and Dobson, Int. J. Epidemiology 34(1), 2005, abstract only (use several baseline points and a control group) [named expert]
- Keep the objective a reading, never a target. Campbell 1976 (Campbell's law) [named expert]; Manheim and Garrabrant, "Categorizing Variants of Goodhart's Law", arXiv:1803.04585 (the risk "grows with the optimization power directed at a proxy") [named expert]; DORA guide [named expert]
- An agent's own judgement that its change worked is not evidence. The verdict rests on a measure outside the agent's control, and the reviewer is not the agent that made the change. Huang et al., "Large Language Models Cannot Self-Correct Reasoning Yet", ICLR 2024 [named expert]; Kamoi et al., "When Can LLMs Actually Correct Their Own Mistakes?", TACL 12, 2024, a critical survey [survey or curated list]; METR, "Recent Frontier Models Are Reward Hacking", 2025-06-05 (agents patched evaluators and tests; "do not cheat" barely changed the rate) [named expert]. No free source found measures agents making process changes for change's sake
- SRE tracks action items to closure ("AIs created vs. closed") and judges effect only by recurrence of a similar incident. It names no review of a closed item's effect. Close items that are "obsolete or infeasible". Lunney et al. 2017 [named expert]; SRE Workbook ch. 10 [named expert]
- ITIL's post-implementation review checks a change against success criteria and a back-out plan set beforehand. The free secondary sources give no interval and no rule for a failed change, so it sets no default here. IT Process Maps, "Checklist Post Implementation Review" [unverified]; AWS Well-Architected, "Change enablement in ITIL 4" [unverified]

## Tools practitioners use

- GitHub sub-issues and issue dependencies hold the parent spec, its tickets and the blocking edges natively, and the `gh` CLI shows them. GitHub.com is hosted and unversioned; gh 2.95.0; both read 2026-10-26. GitHub Docs, "Creating issue dependencies" [standard or field body]
- Pocock's `to-tickets` skill (mattpocock/skills, MIT, about 302k stars; SKILL.md read 2026-10-26 on main at 9e2abf861 of 2026-10-06, after the v1.3.1 release) is a Claude-compatible skill. It drafts tracer-bullet tickets with blocking edges, sequences wide refactors as expand–contract, asks the user to check the breakdown, and then publishes the tickets. It needs its `setup-matt-pocock-skills` tracker configuration. Under the house rule, adopting it needs a proposal ticket. The skill's own file, read for what it does [standard or field body]; stars check a named candidate only [survey or curated list]
- hyperfine benchmarks commands over many runs, with warmup, outlier detection, several commands compared in one run (old against new as a concurrent control) and JSON export. Apache-2.0, v2.0.0, read 2026-10-26, with aarch64-unknown-linux builds. github.com/sharkdp/hyperfine README, which covers what the tool does only [standard or field body]. Its use as the per-batch gate rests on the SRE and Kohavi entries above
