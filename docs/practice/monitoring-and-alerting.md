# monitoring-and-alerting

Researched: 2026-11-19

## Detecting that a job did not work

- Detect a scheduled job's failure from outside it, by the absence of its expected success signal, never by the job reporting its own failure: a job that never starts, hangs or is disabled reports nothing. Prometheus, "Alerting" practices, prometheus.io/docs/practices/alerting/ ("page if the batch job has not succeeded recently enough") [named expert]; Google, *Site Reliability Engineering* ch. 6, sre.google/sre-book/monitoring-distributed-systems/ (black-box monitoring shows "active—not predicted—problems") [named expert]; Healthchecks.io, Dead Man's Snitch and Sentry Crons docs, each one adopter [unverified]
- Give the check an expected period or schedule plus a grace window; for a batch job, alert once it has not succeeded for about two full run cycles. Prometheus as above [named expert]; Healthchecks.io ("grace time") and Cronitor ("Allow jobs to start late"), adopters [unverified]. That the grace must exceed the normal run time plus the scheduler's delay is derived [unverified] and sets no default of its own.
- Send a start signal and an end signal (success, or failure with the exit code), so the monitor tells a missed run from a failed one and catches a run that hangs. Healthchecks.io, healthchecks.io/docs/ (`/start`, `/fail`, `/<exitcode>`); Cronitor, cronitor.io/docs/cron-job-monitoring (a "three-event state machine"); Sentry, docs.sentry.io/product/crons/job-monitoring/ (missed, failed, timeout) [standard or field body], each for its own product. Three vendors converge with no standard behind them, so this sets the mechanism only where one of them is used.
- Alert on the symptom, the result that did not arrive, and carry the cause (disk full, token expired) in the alert text or on a dashboard. SRE book ch. 6 [named expert]; Ewaschuk, "My Philosophy on Alerting", docs.google.com/document/d/199PqyG3UsyXlwieHaqbGiWVa8eMWi8zzAn0YfcApr8Q ("avoid alerting directly on causes") [named expert]; Prometheus practices as above [named expert]
- Research: #5412, its 2026-11-19 research comment (issuecomment-6984301425).

## When a person is told

- Interrupt a person only for what they must act on now; send what can wait as a ticket or report, and keep the rest as a record for a dashboard. SRE book ch. 6 ("Every page should be actionable") and "Practical Alerting", sre.google/sre-book/practical-alerting/ (pages, tickets, "informational data for status dashboards") [named expert]; Ewaschuk as above ("urgent, important, actionable, and real") [named expert]; PagerDuty, "Severity Levels", docs.pagerduty.com/ops-guides/incident-response-guide/severity-levels (SEV-5 is a ticket) [named expert]. Ewaschuk was a Google SRE, so the first two share an origin; PagerDuty is independent.
- So a pass is recorded, not sent. No source says it in words; it is derived from the entry above, and GitHub's "only when a workflow run has failed" setting matches it [unverified]. It sets no default beyond the entry above.
- Group related alerts into one notification, deduplicate repeats of one issue, suppress an alert whose cause another firing alert already reports, and cap how often an unresolved alert repeats. Prometheus Alertmanager docs, prometheus.io/docs/alerting/latest/alertmanager/ (grouping, inhibition) and prometheus.io/docs/alerting/latest/configuration/ (`repeat_interval` default 4h) [standard or field body] for Alertmanager; SRE book "Practical Alerting" [named expert]; PagerDuty, "Reduce Noise", pagerduty.com/ops-guides/ops-practices/reduce-noise/ (`dedup_key`) [named expert]
- Give each alert a short runbook: what it means, its impact, what to do. Ewaschuk as above [named expert]; SRE book "Introduction", sre.google/sre-book/introduction/ (a playbook gives "roughly a 3x improvement in MTTR") [named expert]; Prometheus Operator runbooks' Meaning, Impact and Mitigation pages, one adopter [unverified]. Two sources of one origin: a weak default.
- No source found covers a one-person operation with no on-call rota; the entries above assume a rota and a ticket queue. Read for one person, a page is a push the person sees within the hour, a ticket is a tracker issue, and a record is a log or dashboard line [unverified]; this sets no default.
- Alert fatigue is the reason: where most alerts need no action, people turn them down or ignore them, and a real one is missed. The Joint Commission, Sentinel Event Alert 50 (85–99% of hospital alarm signals need no intervention) [standard or field body], for hospital alarms, the nearest analogue with measurement; Paine et al., *J Hosp Med* 2016, a systematic review (actionable share "<1% to 36%"; evidence for fatigue "emerging") [named expert]; SRE book ch. 6 ("second-guess, skim, or even ignore") [named expert]. IEC 60601-1-8, the medical alarm standard, is paywalled and unread.

## Checking the alert path itself

- Keep one signal that always fires through the real alert path to an observer outside it, which alerts when the signal stops; otherwise a broken alert path looks like a quiet, healthy system. Prometheus Operator runbooks, "Watchdog", runbooks.prometheus-operator.dev/runbooks/general/watchdog/ [standard or field body] for that stack; Volz (PromLabs), "End-to-End Watchdog Alerts", training.promlabs.com [named expert]; ilert, "Prometheus heartbeat example", docs.ilert.com [standard or field body] for its product. That the outside observer tells the person by a channel other than the one under test is derived [unverified] and sets no default.
- Test failover and recovery on a fixed schedule, near production conditions, with the notification step inside the test; a path not exercised is assumed broken. NIST SP 800-34 Rev. 1 §3.5.1, nvlpubs.nist.gov/nistpubs/Legacy/SP/nistspecialpublication800-34r1.pdf ("Notification procedures" in scope; tested "at least annually") [standard or field body]; AWS Well-Architected REL13-BP03 ("the only error recovery that works is the path you test frequently") [named expert], a page AWS keeps "for historical reference only"; SRE book, "Testing for Reliability", sre.google/sre-book/testing-reliability/ ("If you haven't tried it, assume it's broken") [named expert]. Krishnan, "Weathering the Unexpected" (ACM Queue, Google DiRT), refused the fetch and is unread.
- A scheduled test needs the outside check of the first section on its own run, so "the test did not run" is caught as well as "the test failed". Derived from the first section and the entry above [unverified]; it sets no default of its own.

## GitHub Actions schedules

- A `schedule` run can start late under load, most at the top of the hour, and under high load some queued runs may be dropped; it runs only on the default branch. GitHub Docs, "Events that trigger workflows", docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows [standard or field body]. Avoiding minute 0 and giving an outside check over an hour's grace are derived from it [unverified] and set no default.
- In a public repository, scheduled workflows are disabled after 60 days with no repository activity, and a disabled workflow sends nothing. GitHub Docs as above [standard or field body]
- Scheduled-run notifications go to one user: the workflow's creator, then whoever last changed its cron syntax or re-enabled it; each user can choose failure-only. GitHub Docs, "Notifications for workflow runs", docs.github.com/en/actions/concepts/workflows-and-actions/notifications-for-workflow-runs [standard or field body]. That a cron edit by a bot or a second account moves the notices away from the founder is derived from it [unverified].
