# node-and-python-cli-scripts

Researched: 2026-10-22

## Argument parsing and unknown flags

- POSIX Utility Syntax Guidelines: "All options should precede operands on the command line" (Guideline 9). "The first -- argument that is not an option-argument should be accepted as a delimiter indicating the end of options. Any following arguments should be treated as operands, even if they begin with the '-' character" (Guideline 10). pubs.opengroup.org/onlinepubs/9799919799/basedefs/V1_chap12.html §12.2 [standard or field body]
- Node `util.parseArgs` is stable since v20.0.0. `strict` defaults to `true`: it throws "when unknown arguments are encountered, or when arguments are passed that do not match the `type`". With `tokens: true` it returns an `option-terminator` token for `--`. Thus keep `strict` on; do not hand-parse `process.argv`. nodejs.org/api/util.html §util.parseArgs([config]) [standard or field body]
- Python `argparse`: `parse_args()` prints "error: unrecognized arguments: --bar" to `sys.stderr` and exits with status 2. `parse_known_args()` does not refuse unknown arguments; use it only on purpose. `allow_abbrev` defaults to `True`, so `--fo` matches `--foo`; set `allow_abbrev=False` to refuse prefixes. `'--'` "tells `parse_args()` that everything after that is a positional argument". `exit_on_error=False` (3.9+) lets a test catch `ArgumentError`. docs.python.org/3/library/argparse.html [standard or field body]
- clig.dev: "Use a command-line argument parsing library where you can"; "Prefer flags to args", because flags "make it much clearer what is going on"; "If the user did something wrong and you can guess what they meant, suggest it." clig.dev §Arguments and flags [named expert]

## Arguments through `npm run` and the `--` separator

- npm: "Use `--` to pass `-`-prefixed flags and options which would otherwise be parsed by npm", for example `npm run test -- --grep="pattern"`. "The arguments will only be passed to the script specified after `npm run` and not to any `pre` or `post` script." Without `--`, npm takes a dash flag as its own config. docs.npmjs.com/cli/v10/commands/npm-run-script [standard or field body]
- npm runs the script line through `sh` (`script-shell`, default `/bin/sh` on POSIX), from the package root, "regardless of what the current working directory is"; `INIT_CWD` holds the caller's directory. "If the script exits with a code other than 0, then this will abort the process." docs.npmjs.com/cli/v10/using-npm/scripts; docs.npmjs.com/cli/v10/commands/npm-run-script [standard or field body]
- npm prints a `> pkg@x script` banner; `-s` / `--silent` is `--loglevel silent`. The npm maintainers say a script spawned with `stdio: inherit` can still write to stdout, and recommend `--silent` when a caller must parse clean stdout. docs.npmjs.com/cli/v10/using-npm/config §loglevel; github.com/npm/cli/pull/7439 [standard or field body]
- Node `node --run <script>` (added v22.0.0): "Any argument after `--` will be appended to the script", for example `node --run test -- --verbose`. It intentionally does not run `pre`/`post` scripts or set npm's `npm_*` variables. nodejs.org/api/cli.html §--run [standard or field body]
- Thus: a script that needs a flag from `npm run` documents the form `npm run <name> -- --flag`; a caller that parses the output uses `npm run -s` or calls `node scripts/x.js` directly. A script must not read `npm_*` variables if it can also run by `node` or `node --run`. Derived from the rows above [unverified]

## Exit codes, stdout and stderr

- clig.dev: "Return zero exit code on success, non-zero on failure." "Send output to `stdout`." "Send messaging to `stderr`." clig.dev §The Basics, §Output [named expert]
- GNU Coding Standards: error messages take the form `program: message` or `program:sourcefile:lineno: message`. "All programs should support two standard options: '--version' and '--help'"; `--help` output goes "on standard output". gnu.org/prep/standards/html_node/Errors.html; …/Command_002dLine-Interfaces.html; …/_002d_002dhelp.html [standard or field body]
- Bash: exit status is 0 to 255; "All builtins return an exit status of 2 to indicate incorrect usage". argparse also exits 2 on a usage error. gnu.org/software/bash/manual/html_node/Exit-Status.html; docs.python.org/3/library/argparse.html [standard or field body]
- `sysexits.h` exists, but FreeBSD says "This interface has been deprecated and is retained only for compatibility. Its use is discouraged." Thus use 0, 1 and 2 (usage), and keep other codes for a caller that documents them. man.freebsd.org sysexits(3) [standard or field body]
- Claude Code hooks: exit 0 means success, and stdout is JSON output only when it is one JSON object; "Claude never sees stderr from a hook that exits 0". Exit 2 blocks, and stderr is the block message. Any other code is a non-blocking error: "Exit code 1 without valid JSON output is a non-blocking error ... If your hook is meant to enforce a policy, use `exit 2`." code.claude.com/docs/en/hooks §Exit code output [standard or field body]
- Node: `process.exit()` exits "even if there are still asynchronous operations pending ..., including I/O operations to `process.stdout` and `process.stderr`", so output "could lead to data ... being truncated and lost". The code "should set the `process.exitCode` and allow the process to exit naturally". On POSIX, writes to pipes and sockets are asynchronous; to files and TTYs they are synchronous. nodejs.org/api/process.html §process.exit([code]), §A note on process I/O [standard or field body]

## Dry-run and one-shot jobs that must act at most once

- clig.dev defines `-n, --dry-run`: "Do not run the command, but describe the changes that would occur if the command were run." Robustness: operations "should be idempotent where possible"; "Make it recoverable" (run it again and it "should pick up from where it left off"). clig.dev §Arguments and flags, §Robustness [named expert]
- Henrik Warne (2026-01-31): put the flag check in each major phase, which prints the step in place of doing it; the worker code does not read the flag. henrikwarne.com/2026/01/31/in-praise-of-dry-run/ [named expert]
- Do not check and then act. Node: "Do not use `fs.access()` to check for the accessibility of a file before calling `fs.open()` ... Doing so introduces a race condition ... user code should open/read/write the file directly and handle the error". nodejs.org/api/fs.html §fs.access [standard or field body]
- Claim with one atomic create. open(2): with `O_CREAT | O_EXCL`, if the path exists, "`open()` fails with the error `EEXIST`". Node flag `'wx'`: "Like `'w'` but fails if the path exists"; "The exclusive flag might not work with network file systems." So plain `fs.openSync(path, 'wx')` is enough on a local disk with no takeover. man7.org/linux/man-pages/man2/open.2.html; nodejs.org/api/fs.html §File system flags [standard or field body]
- Stale-lock takeover needs a liveness signal. proper-lockfile uses `mkdir` ("works atomically on any kind of file system, even network based ones"), refreshes the lock `mtime` every `stale/2`, takes over a lock older than `stale` (default 10000 ms, minimum 5000 ms), and calls `onCompromised` when the refresh fails. github.com/moxystudio/node-proper-lockfile README [survey or curated list]
- Python `filelock`: `FileLock` uses a kernel lock (`fcntl.flock`, `LockFileEx`), "Released automatically on crash"; `SoftFileLock` is a "file-existence marker" that reclaims only when the owner is "provably-gone"; `StrictSoftFileLock` "Never guesses that an owner died". py-filelock.readthedocs.io [survey or curated list]
- Kleppmann: a lease-based lock is not safe alone. If the holder pauses longer than the lease, "Clients 1 and 2 now both believe they hold the lock". The fix is a "fencing token", "a number that increases", that the store checks on each write. martin.kleppmann.com/2016/02/08/how-to-do-distributed-locking.html [named expert]
- Derived: for "at most once", write the claim marker before the act; a crash after the claim then leaves the job not done, which is the safe side for a one-shot job [unverified]

## A daemon taking up new code

- Prove the new code starts before the old stops, and keep the old runnable until then. nginx's binary upgrade (`USR2`) starts the new master beside the old, which "does not close its listen sockets"; a failing new master is sent `TERM` and the old one carries on. nginx.org/en/docs/control.html §Upgrading Executable on the Fly [standard or field body]
- Carry state across a re-exec explicitly. `systemctl daemon-reexec` will "serialize the manager state, reexecute the process and deserialize the state again". freedesktop.org/software/systemd/man/latest/systemctl.html [standard or field body]
- One upgrade at a time. Cloudflare's tableflip waits for the new process to report ready, die or time out. blog.cloudflare.com/graceful-upgrades-in-go/ [named expert]
- Node's `process.execve(file, args, env)` (v23.11.0, Stability 1) replaces the image under the same pid "without triggering any exit or close events" and keeps only stdin, stdout and stderr; a failed `execve(2)` throws and "the current process continues to run with its state unchanged". So any cleanup runs first, and any other open handle is reopened by the new image. nodejs.org/api/process.html §process.execve [standard or field body]

## Testing CLI scripts

- Keep the entry guard small so a test can import the script. Python: "If a module like this was imported ... for example to unit test it, the script code would unintentionally execute"; put "as few statements as possible" under `if __name__ == '__main__'`, and write `sys.exit(main())` with `main()` that returns an int. docs.python.org/3/library/__main__.html [standard or field body]
- Node: `import.meta.main` (v24.2.0, Stability 1.0) is "Equivalent to `require.main === module` in CommonJS" and "Analogous to Python's `__name__ == "__main__"`"; its example: `if (import.meta.main) main();` so that a function "can be imported from another module without possible side-effects". nodejs.org/api/esm.html §import.meta.main [standard or field body]
- In-process runners are the field tools. Click `CliRunner` captures output "by replacing `sys.stdout` and `sys.stderr` with in-memory wrappers"; it "change[s] the entire interpreter state", is "not thread-safe", and Click recommends process isolation (pytest-xdist) for parallel runs. oclif's `@oclif/test`: `const {stdout} = await runCommand('whoami')`, and the error carries the exit code (`error?.oclif?.exit`). click.palletsprojects.com/en/stable/testing/; oclif.io/docs/testing/ [standard or field body]
- Capture at the right level. pytest `capsys` takes Python-level writes; `capfd` takes file descriptors 1 and 2 and so "also capture[s] output from libraries or subprocesses". docs.pytest.org/en/stable/how-to/capture-stdout-stderr.html [standard or field body]
- Inject the clock. Node `mock.timers.enable({ apis: ['Date', 'setTimeout'], now })` fakes `Date` and timers on one clock, and the test-context mock is restored "once the test finishes". It does not support a destructured `import { setTimeout } from 'node:timers'`. A child process keeps its real clock, so give the script a `now` input. nodejs.org/api/test.html §Mocking, §Timers; see test-design-and-reliability §Time [standard or field body]
- Environment and external commands: give a spawned child an explicit `env`; stub a binary with a fake earlier on `PATH` (pytest `monkeypatch.setenv(..., prepend=os.pathsep)`, bats-mock). docs/practice/test-design-and-reliability.md §Tests that spawn real processes or scripts [standard or field body]
- Test most cases in process through a `main(argv, env, deps)` that returns an exit code, and keep a few child-process tests that prove the real entry point, the exit code and the stream split. Derived [unverified]

## Interactive terminal panels

- Keep desired and observed state apart. Kubernetes: `spec` is "the specification of the desired state", `status` holds "the most recent observations of actual state"; `observedGeneration` is "the `generation` most recently observed by the component responsible for acting upon changes". github.com/kubernetes/community …/api-conventions.md [standard or field body]
- A queued request is not a done one. `systemctl --no-block`: "Do not synchronously wait for the requested operation to finish". Units show transition states (`activating`, `deactivating`, `reloading`). freedesktop.org/software/systemd/man/latest/systemctl.html [standard or field body]
- Field TUIs mark the item while the act is in flight: lazygit draws a spinner on the item (`WithInlineStatus`); lazydocker shows a present-participle word ("restarting", "stopping") until the act returns; k9s dims a deleted row (`AttrDim`) until the watch removes it, and flashes a line for 6 s. github.com/jesseduffield/lazygit, /lazydocker, github.com/derailed/k9s (source) [survey or curated list]
- Response times: 0.1 s feels instant; over 1 s, "indicate to the user that the computer is working"; 10 s is the attention limit, past which the wait needs progress and "a clearly signposted way for the user to interrupt". A looped animation suits 2-10 s. nngroup.com/articles/response-times-3-important-limits/; nngroup.com/articles/progress-indicators/ [named expert]
- Show a toggle's state and its action as two elements: "The safest solution is to use 2 UI elements, one for current state and another one for the switch-state action" (Budiu). Label it with a noun (Microsoft); never show state by colour alone, and prefer checkboxes for a list of on/off items (Apple HIG). nngroup.com/articles/state-switch-buttons/; learn.microsoft.com/en-us/windows/apps/design/controls/toggles; developer.apple.com/design/human-interface-guidelines/toggles, both vendors' reasoned guidance [named expert]
- Confirm only serious acts, and label the choices with their results ("Delete file", "Keep file"), not Yes/No; too many confirmations and "people will stop paying attention". Prefer undo. nngroup.com/articles/confirmation-dialog/ [named expert]
- Layout: state at the top, a bottom key-hint line, `?` for full help, `q` to quit, `:` for free text. nano-editor.org/dist/latest/nano.html; man7.org/linux/man-pages/man1/htop.1.html; github.com/jesseduffield/lazygit docs/Config.md; k9scli.io/topics/commands/; github.com/aristocratos/btop [standard or field body; adoption survey or curated list]
- Mouse: Windows Terminal "supports mouse input in Windows Subsystem for Linux (WSL) applications", and Shift held selects text while a program is in mouse mode. Its source handles modes 1000, 1002, 1003, 1004, 1006 and 1049. Open issues: a click that focuses the pane also reaches the program (#5310); no tracking while unfocused (#6538). learn.microsoft.com/en-us/windows/terminal/selection; github.com/microsoft/terminal [standard or field body]
- SGR mouse reports are `CSI < b ; x ; y M` on press and `m` on release (mode 1006), which lifts the X10 limit of 223 columns. Node's `readline` does not decode them, so parse the raw stream. invisible-island.net/xterm/ctlseqs/ctlseqs.html §Mouse Tracking [standard or field body]
- Raw mode: `setRawMode(true)` gives input "character-by-character", and "Ctrl+C will no longer cause a `SIGINT`", so the program handles `\x03` itself. `hasColors()` honours `NO_COLOR`, which covers colour only, not bold or inverse. nodejs.org/api/tty.html; no-color.org [standard or field body]
- Restore the terminal on every exit, a crash included: leave the alternate screen, show the cursor, turn raw mode and mouse modes off, and never throw while restoring. ratatui.rs/recipes/apps/panic-hooks/; github.com/vadimdemedes/ink README [survey or curated list]
- Thus, for a panel over a daemon: draw the observed value as the fact with a pending mark beside it (elapsed time after 10 s; a second press undoes); clear the mark only when a status read shows the change; acknowledge a key within 0.1 s; act on mouse release in the pressed cell and ignore the press that focused the pane; keep every control on a key; confirm only a stop, with result-labelled keys. Derived from the rows above [unverified]
