# node-and-python-cli-scripts

Researched: 2026-10-22

## Argument parsing and unknown flags

- POSIX Utility Syntax Guidelines: "All options should precede operands on the command line" (Guideline 9). "The first -- argument that is not an option-argument should be accepted as a delimiter indicating the end of options. Any following arguments should be treated as operands, even if they begin with the '-' character" (Guideline 10). pubs.opengroup.org/onlinepubs/9799919799/basedefs/V1_chap12.html §12.2 [standard or field body]
- Node `util.parseArgs` is stable since v20.0.0. `strict` defaults to `true`: it throws "when unknown arguments are encountered, or when arguments are passed that do not match the `type`". With `tokens: true` it returns an `option-terminator` token for `--`. Thus keep `strict` on; do not hand-parse `process.argv`. nodejs.org/api/util.html §util.parseArgs([config]) [standard or field body]
- Python `argparse`: `parse_args()` prints "error: unrecognized arguments: --bar" to `sys.stderr` and exits with status 2. `parse_known_args()` does not refuse unknown arguments; use it only on purpose. `allow_abbrev` defaults to `True`, so `--fo` matches `--foo`; set `allow_abbrev=False` to refuse prefixes. `'--'` "tells `parse_args()` that everything after that is a positional argument". `exit_on_error=False` (3.9+) lets a test catch `ArgumentError`. docs.python.org/3/library/argparse.html [standard or field body]
- clig.dev: "Use a command-line argument parsing library where you can"; "Prefer flags to args", because flags "make it much clearer what is going on"; "If the user did something wrong and you can guess what they meant, suggest it." clig.dev §Arguments and flags [named expert]

## Arguments through `npm run` and the `--` separator

- npm: "Use `--` to pass `-`-prefixed flags and options which would otherwise be parsed by npm", for example `npm run test -- --grep="pattern"`. "The arguments will only be passed to the script specified after `npm run` and not to any `pre` or `post` script." Without `--`, npm takes a dash flag as its own config. docs.npmjs.com/cli/v10/commands/npm-run-script [standard or field body]
- npm runs the script line through `sh` (`script-shell`, default `/bin/sh` on POSIX), from the package root, "regardless of what the current working directory is"; `INIT_CWD` holds the caller's directory. "If the script exits with a code other than 0, then this will abort the process." docs.npmjs.com/cli/v10/using-npm/scripts; docs.npmjs.com/cli/v10/commands/npm-run-script [standard or field body]
- npm prints a `> pkg@x script` banner; `-s` / `--silent` is `--loglevel silent`. The npm maintainers say a script spawned with `stdio: inherit` can still write to stdout, and recommend `--silent` when a caller must parse clean stdout. docs.npmjs.com/cli/v10/using-npm/config §loglevel; github.com/npm/cli/pull/7439 [standard or field body]
- Node `node --run <script>` (added v22.0.0): "Any argument after `--` will be appended to the script", for example `node --run test -- --verbose`. It intentionally does not run `pre`/`post` scripts or set npm's `npm_*` variables. nodejs.org/api/cli.html §--run [standard or field body]
- Thus: a script that needs a flag from `npm run` documents the form `npm run <name> -- --flag`; a caller that parses the output uses `npm run -s` or calls `node scripts/x.js` directly. A script must not read `npm_*` variables if it can also run by `node` or `node --run`. Derived from the rows above, so it sets no default [unverified]

## Exit codes, stdout and stderr

- clig.dev: "Return zero exit code on success, non-zero on failure." "Send output to `stdout`." "Send messaging to `stderr`." clig.dev §The Basics, §Output [named expert]
- GNU Coding Standards: error messages take the form `program: message` or `program:sourcefile:lineno: message`. "All programs should support two standard options: '--version' and '--help'"; `--help` output goes "on standard output". gnu.org/prep/standards/html_node/Errors.html; …/Command_002dLine-Interfaces.html; …/_002d_002dhelp.html [standard or field body]
- Bash: exit status is 0 to 255; "All builtins return an exit status of 2 to indicate incorrect usage". argparse also exits 2 on a usage error. gnu.org/software/bash/manual/html_node/Exit-Status.html; docs.python.org/3/library/argparse.html [standard or field body]
- `sysexits.h` exists, but FreeBSD says "This interface has been deprecated and is retained only for compatibility. Its use is discouraged." Thus use 0, 1 and 2 (usage), and keep other codes for a caller that documents them. man.freebsd.org sysexits(3) [standard or field body]
- Claude Code hooks: exit 0 means success, and stdout is JSON output only when it is one JSON object; "Claude never sees stderr from a hook that exits 0". Exit 2 blocks, and stderr is the block message. Any other code is a non-blocking error: "Exit code 1 without valid JSON output is a non-blocking error ... If your hook is meant to enforce a policy, use `exit 2`." code.claude.com/docs/en/hooks §Exit code output [standard or field body]
- Node: `process.exit()` exits "even if there are still asynchronous operations pending ..., including I/O operations to `process.stdout` and `process.stderr`", so output "could lead to data ... being truncated and lost". The code "should set the `process.exitCode` and allow the process to exit naturally". On POSIX, writes to pipes and sockets are asynchronous; to files and TTYs they are synchronous. nodejs.org/api/process.html §process.exit([code]), §A note on process I/O [standard or field body]

## Dry-run and one-shot jobs that must act at most once

- clig.dev defines `-n, --dry-run`: "Do not run the command, but describe the changes that would occur if the command were run." Robustness: operations "should be idempotent where possible"; "Make it recoverable" (run it again and it "should pick up from where it left off"). clig.dev §Arguments and flags, §Robustness [named expert]
- Henrik Warne (2026-01-31): put the flag check in each major phase, which prints the step in place of doing it; the worker code does not read the flag. henrikwarne.com/2026/01/31/in-praise-of-dry-run/ [named expert]
- Do not check and then act. Node: "Do not use `fs.access()` to check for the accessibility of a file before calling `fs.open()` ... Doing so introduces a race condition ... user code should open/read/write the file directly and handle the error". nodejs.org/api/fs.html §fs.access [standard or field body]
- Claim with one atomic create. open(2): with `O_CREAT | O_EXCL`, if the path exists, "`open()` fails with the error `EEXIST`". Node flag `'wx'`: "Like `'w'` but fails if the path exists"; "The exclusive flag might not work with network file systems." So plain `fs.openSync(path, 'wx')` is enough on a local disk with no takeover. man7.org/linux/man-pages/man2/open.2.html; nodejs.org/api/fs.html §File system flags [standard or field body]
- Stale-lock takeover needs a liveness signal. proper-lockfile uses `mkdir` ("works atomically on any kind of file system, even network based ones"), refreshes the lock `mtime` every `stale/2`, takes over a lock older than `stale` (default 10000 ms, minimum 5000 ms), and calls `onCompromised` when the refresh fails. github.com/moxystudio/node-proper-lockfile README. One adopter, no default [unverified]
- Python `filelock`: `FileLock` uses a kernel lock (`fcntl.flock`, `LockFileEx`), "Released automatically on crash"; `SoftFileLock` is a "file-existence marker" that reclaims only when the owner is "provably-gone"; `StrictSoftFileLock` "Never guesses that an owner died". py-filelock.readthedocs.io [standard or field body]
- Kleppmann: a lease-based lock is not safe alone. If the holder pauses longer than the lease, "Clients 1 and 2 now both believe they hold the lock". The fix is a "fencing token", "a number that increases", that the store checks on each write. martin.kleppmann.com/2016/02/08/how-to-do-distributed-locking.html [named expert]
- Derived: for "at most once", write the claim marker before the act; a crash after the claim then leaves the job not done, which is the safe side for a one-shot job, so it sets no default [unverified]

## Measuring elapsed time

- Time a span on a monotonic clock, never as a difference of wall-clock readings. The wall clock "may not always be monotonically increasing", so a difference of two `Date.now()` values can be positive, negative or zero for one span; the monotonic clock "should be used for measurement, rather than user-visible times". In Node that is `performance.now()`. w3.org/TR/hr-time-3/ §1, §2.1 [standard or field body]
- Linux: `CLOCK_REALTIME` "is affected by discontinuous jumps in the system time"; `CLOCK_MONOTONIC` is not, and "does not count time that the system is suspended"; `CLOCK_BOOTTIME` is monotonic and does count it. So pick `CLOCK_BOOTTIME` only where suspended time must count. man7.org/linux/man-pages/man2/clock_gettime.2.html [standard or field body]
- Python: a program timing a timeout or a duration on system time "may fail to run events at the right moment or stop the timeout too early or too late"; use `time.monotonic()`. peps.python.org/pep-0418/ [named expert]

## Where a CLI keeps credentials

- Per-user config goes under `$XDG_CONFIG_HOME`: "If `$XDG_CONFIG_HOME` is either not set or empty, a default equal to `$HOME`/.config should be used." "All paths set in these environment variables must be absolute"; a relative one is "invalid" and ignored. A missing directory is created "with permission `0700`"; an existing one's permissions "should not be changed". specifications.freedesktop.org/basedir/latest/ [standard or field body]
- OWASP's Secrets Management Cheat Sheet treats secrets "hardcoded within the source code" as the problem to solve, and advises "secrets detection at the developer level to avoid checking secrets into code before commit/PR". cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html [standard or field body]
- Adopters of a per-user location outside any project: `gh` keeps its config at `$XDG_CONFIG_HOME/gh`, else `$HOME/.config/gh` (cli.github.com/manual/gh_help_environment); the AWS CLI keeps credentials in `~/.aws/credentials` (docs.aws.amazon.com/cli/latest/userguide/cli-configure-files.html). [unverified]
- Thus: a CLI's stored secret lives in a per-user file under `$XDG_CONFIG_HOME/<tool>/`, owner-only, never in a working tree. A gitignored `.env` in the repo root keeps it out of commits but not out of reach of a stray write.

## Regexes that backtrack

- OWASP: a regex is "evil" when it holds a repeated group whose inside repeats again or has alternatives that overlap, such as `(a+)+$` or `(a|aa)+$`. An input that almost matches can then "hang the system". owasp.org/www-community/attacks/Regular_expression_Denial_of_Service_-_ReDoS [standard or field body]
- Stack Overflow's 2016 outage: a trailing-run pattern such as `\s+$` is quadratic on a long run that does not end the input: the engine restarts it at each character of the run. stackstatus.net/post/147710624694 [named expert]
- Thus, on input the script did not write (issue bodies, `gh` output, a transcript): cut a trailing run with `trimEnd()` or a one-pass loop, not with `/x+$/`. Give a quantifier alternatives that cannot both match one character. In a hook, test for a hang with a process timeout, because a regex match blocks and nothing in the same process can stop it. Derived from the two rows above, so it sets no default [unverified]

## Testing CLI scripts

- Keep the entry guard small so a test can import the script. Python: "If a module like this was imported ... for example to unit test it, the script code would unintentionally execute"; put "as few statements as possible" under `if __name__ == '__main__'`, and write `sys.exit(main())` with `main()` that returns an int. docs.python.org/3/library/__main__.html [standard or field body]
- Node: `import.meta.main` (v24.2.0, Stability 1.0) is "Equivalent to `require.main === module` in CommonJS" and "Analogous to Python's `__name__ == "__main__"`"; its example: `if (import.meta.main) main();` so that a function "can be imported from another module without possible side-effects". nodejs.org/api/esm.html §import.meta.main [standard or field body]
- In-process runners are the field tools. Click `CliRunner` captures output "by replacing `sys.stdout` and `sys.stderr` with in-memory wrappers"; it "change[s] the entire interpreter state", is "not thread-safe", and Click recommends process isolation (pytest-xdist) for parallel runs. oclif's `@oclif/test`: `const {stdout} = await runCommand('whoami')`, and the error carries the exit code (`error?.oclif?.exit`). click.palletsprojects.com/en/stable/testing/; oclif.io/docs/testing/, each for what it does [standard or field body]; that they are the field's tools rests on the two as adopters, so it sets no default [unverified]
- Capture at the right level. pytest `capsys` takes Python-level writes; `capfd` takes file descriptors 1 and 2 and so "also capture[s] output from libraries or subprocesses". docs.pytest.org/en/stable/how-to/capture-stdout-stderr.html [standard or field body]
- Inject the clock. Node `mock.timers.enable({ apis: ['Date', 'setTimeout'], now })` fakes `Date` and timers on one clock, and the test-context mock is restored "once the test finishes". It does not support a destructured `import { setTimeout } from 'node:timers'`. A child process keeps its real clock, so give the script a `now` input. nodejs.org/api/test.html §Mocking, §Timers; see test-design-and-reliability §Time [standard or field body]
- Environment and external commands: give a spawned child an explicit `env`; stub a binary with a fake earlier on `PATH` (pytest `monkeypatch.setenv(..., prepend=os.pathsep)`). docs/practice/test-design-and-reliability.md §Tests that spawn real processes or scripts [standard or field body]
- Test most cases in process through a `main(argv, env, deps)` that returns an exit code, and keep a few child-process tests that prove the real entry point, the exit code and the stream split. Derived, so it sets no default [unverified]

## Interactive terminal panels

- Keep desired and observed state apart. Kubernetes: `spec` is "the specification of the desired state", `status` holds "the most recent observations of actual state"; `observedGeneration` is "the `generation` most recently observed by the component responsible for acting upon changes". github.com/kubernetes/community …/api-conventions.md [named expert]
- A queued request is not a done one. `systemctl --no-block`: "Do not synchronously wait for the requested operation to finish". Units show transition states (`activating`, `deactivating`, `reloading`). freedesktop.org/software/systemd/man/latest/systemctl.html. One adopter, no default [unverified]
- Field TUIs mark the item while the act is in flight: lazygit draws a spinner on the item; lazydocker shows a present-participle word ("restarting", "stopping") until the act returns; k9s dims a deleted row until the watch removes it. github.com/jesseduffield/lazygit, /lazydocker, github.com/derailed/k9s (source). Three adopters, no default [unverified]
- Response times: 0.1 s feels instant; over 1 s, "indicate to the user that the computer is working"; 10 s is the attention limit, past which the wait needs progress and "a clearly signposted way for the user to interrupt". A looped animation suits 2-10 s. nngroup.com/articles/response-times-3-important-limits/; nngroup.com/articles/progress-indicators/ [named expert]
- Show a toggle's state and its action as two elements: "The safest solution is to use 2 UI elements, one for current state and another one for the switch-state action" (Budiu). Label it with a noun (Microsoft); never show state by colour alone, and prefer checkboxes for a list of on/off items (Apple HIG). nngroup.com/articles/state-switch-buttons/; learn.microsoft.com/en-us/windows/apps/design/controls/toggles; developer.apple.com/design/human-interface-guidelines/toggles, both vendors' reasoned guidance [named expert]
- Confirm only serious acts, and label the choices with their results ("Delete file", "Keep file"), not Yes/No; too many confirmations and "people will stop paying attention". Prefer undo. nngroup.com/articles/confirmation-dialog/ [named expert]
- Layout: state at the top, a bottom key-hint line, `?` for full help, `q` to quit, `:` for free text. nano-editor.org/dist/latest/nano.html; man7.org/linux/man-pages/man1/htop.1.html; github.com/jesseduffield/lazygit docs/Config.md; k9scli.io/topics/commands/; github.com/aristocratos/btop. Five adopters, no default [unverified]
- Mouse: Windows Terminal "supports mouse input in Windows Subsystem for Linux (WSL) applications", and Shift held selects text while a program is in mouse mode. Its source handles modes 1000, 1002, 1003, 1004, 1006 and 1049. Open issues: a click that focuses the pane also reaches the program (#5310); no tracking while unfocused (#6538). learn.microsoft.com/en-us/windows/terminal/selection; github.com/microsoft/terminal [standard or field body]
- SGR mouse reports are `CSI < b ; x ; y M` on press and `m` on release (mode 1006), which lifts the X10 limit of 223 columns. Node's `readline` does not decode them, so parse the raw stream. Wheel mice "may return buttons 4 and 5", coded as buttons 1 and 2 with 64 added, so 64 and 65 before modifiers, and "Release events for the wheel buttons are not reported". invisible-island.net/xterm/ctlseqs/ctlseqs.html §Mouse Tracking [standard or field body]
- Raw mode: `setRawMode(true)` gives input "character-by-character", and "Ctrl+C will no longer cause a `SIGINT`", so the program handles `\x03` itself. `hasColors()` honours `NO_COLOR`, which covers colour only, not bold or inverse. nodejs.org/api/tty.html; no-color.org [standard or field body]
- Restore the terminal on every exit, a crash included: leave the alternate screen, show the cursor, turn raw mode and mouse modes off, and never throw while restoring. ratatui.rs/recipes/apps/panic-hooks/ [named expert]; github.com/vadimdemedes/ink README, one adopter [unverified]
- Thus, for a panel over a daemon: draw the observed value as the fact with a pending mark beside it (elapsed time after 10 s; a second press undoes); clear the mark only when a status read shows the change; acknowledge a key within 0.1 s; act on mouse release in the pressed cell and ignore the press that focused the pane; keep every control on a key; confirm only a stop, with result-labelled keys. Derived from the rows above, so it sets no default [unverified]

## Start-up cost of a command run often

Researched: 2026-11-11 for this section.

- Deferred `require()`: "some style guides prescribe that it should be called only in the top level of a module", "to make it easier to identify dependencies"; the exception is a module "only used in very rare situations and will cause significant overhead to load it." eslint.org/docs/latest/rules/global-require [named expert]
- Rush Stack `Import.lazy()`: "Provides a way to improve process startup times by lazy-loading imported modules"; the load "occurs here, only if needed". "Never apply lazy-loading in a way that would convert the module's type to any." Lazy imports go in one group after the normal ones. api.rushstack.io/pages/node-core-library.import.lazy/ [named expert]
- Babel's `lazy` option: "evaluating dependencies up front is sometimes entirely un-necessary." "Local paths are much more likely to have circular dependencies, which may break if loaded lazily"; a side-effect import is never lazy. babeljs.io/docs/babel-plugin-transform-modules-commonjs [named expert]
- React Native: "Inlining `require` calls changes the order in which modules are evaluated, and can even cause some modules to _never_ be evaluated." reactnative.dev/docs/optimizing-javascript-loading [named expert]
- Shopify CLI: "the more significant the graph is, the more the CLI takes to load"; its decision is to "lazily import the module when needed". shopify.github.io/cli/decision-record/2022-12-21-dynamically-importing-lodash-using-commonjs.html [named expert]
- A later `require()` of a loaded module is free: "Modules are cached after the first time they are loaded." nodejs.org/api/modules.html [standard or field body]
- Compile cache (`NODE_COMPILE_CACHE`, v22.1.0; `module.enableCompileCache()`, v22.8.0; stable from v24.15.0): it "may slow down the first load of a module graph, but subsequent loads of the same module graph may get a significant speedup". It stores only "the result of parsing + compilation"; resolution, file reads and execution remain. "there is no substitute for profiling." nodejs.org/docs/latest-v24.x/api/module.html [standard or field body]; v8.dev/blog/code-caching-for-devs [named expert]. Measured here on Node v24.18: 7% of the CPU of a 244-module load (#4821).
- Measure with `--cpu-prof`, stable since v22.4.0: it "Starts the V8 CPU profiler on start up, and writes the CPU profile to disk before exit"; `--cpu-prof-interval` defaults to 1000 microseconds. nodejs.org/api/cli.html [standard or field body]
- A log's newest line: `fs.read` at a non-negative `position` reads from there; "it is better to use `fs.read()` directly" when speed matters. nodejs.org/api/fs.html [standard or field body]
- Budget: "Print something to the user in <100ms." clig.dev [named expert]. No source gives a budget for a polled command.
- Thus: keep `require()` at the top level by default. For a command run every few seconds, profile first; then move what it never calls out of its load path, by a module split where the code divides cleanly and by a `require()` inside the one function that uses a rare, heavy module, with a comment saying why. Never defer a module loaded for its side effects. Pin the load set with a test, because a later top-level `require` undoes the cut unseen. Read a large append-only log's last row from its end.
