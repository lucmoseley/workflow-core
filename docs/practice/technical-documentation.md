# technical-documentation

Researched: 2026-11-09

Scope: code comments, file headers, suppression comments and decision records in a Node, Python and shell CLI repo. Three independent sources agree on each bullet unless it says otherwise.

## Code comments

- Do not write a comment that restates what the code, or a search over it, already says. Spencer, "Best practices for writing code comments" (stackoverflow.blog, 2021-12-23, Rule 1: "Comments should not duplicate the code", one with no new information "can become out-of-date"); Google C++ Style Guide, Comments (google.github.io/styleguide/cppguide.html: "Do not state the obvious"; declaration comments are not repeated at the definition); Martin, in Ousterhout and Martin, aposd-vs-clean-code (github.com/johnousterhout/aposd-vs-clean-code: "I look at every comment as potential misinformation"; the best comments say something "surprising and verifiable") [named expert]
- Use a comment for what the code cannot show: why it is so, a constraint, a non-obvious invariant. Ousterhout, aposd-vs-clean-code ("important information that is not obvious from the code"); Google C++ Style Guide ("describe why the code does what it does"); Spencer 2021 (Rule 5: "Explain unidiomatic code in comments") [named expert]
- Who calls a module is a question a reference search answers live; a hand-kept caller list in a header is a second copy of it that drifts with every move. Tool docs show caller lookup as an on-demand query (LispWorks `who-calls`; Embarcadero RAD Studio, Find References). No source states this for caller lists in these words, so it sets no default beyond the first bullet's [unverified]
- Ousterhout disagrees on staleness: he has "not found them be a significant problem" and holds comments easy to keep current. His view weighs against cutting comments that carry design reasons, not against copies of derivable facts. aposd-vs-clean-code [named expert]

## Comments, workarounds and agents

Researched: 2026-11-21 for this section.

- A comment that explains unclear code of our own is a signal to change the code first: extract, rename or assert, and the comment is no longer needed. Fowler and Beck, *Refactoring* 2nd ed. ch. 3, InformIT excerpt (informit.com/articles/article.aspx?p=2952392&seqNum=24: comments "are often used as a deodorant"; "first try to refactor the code so that any comment becomes superfluous"; Introduce Assertion for a rule about system state); Ford, "Comments == Code Smell" (nealford.com, 2008-11-07: pervasive comments add "friction" to refactoring); Ousterhout, *A Philosophy of Software Design* ch. 15 through reader summaries (a method that "requires a long comment" is "a red flag that you don't have a good abstraction") [named expert]
- Coding agents over-comment by default. OpenAI Codex CLI prompts (github.com/openai/codex, `codex-rs/core/gpt_5_2_prompt.md`: "Do not add inline comments within code unless explicitly requested"), Google Gemini CLI prompts (github.com/google-gemini/gemini-cli, `snippets.legacy.ts`: "Add code comments sparingly"), Anthropic, "Prompting best practices", Overeagerness (platform.claude.com: "Don't add docstrings, comments, or type annotations to code you didn't change") [standard or field body, each for its own agent]; Ye, Ran, Xu and Zhou, arXiv:2605.13280 (2026: LLM code shows "Excessive Complexity and Redundant Comments") [named expert]
- Agents act on what comments say, stale ones included: 13% of sessions meet a bug-citing TODO or FIXME, 6% of those act on the bug, mostly unasked, and over two-fifths of those detours chase a closed ticket, at 77% more tokens. Saccone and Garikapati, "Agent Distraction" (developers.googleblog.com, 2026-11-06, from "hundreds of millions of agent steps") [named expert]. One measured source; their remedy is an automated cleaner that removes a TODO once its intent is confirmed obsolete
- The claim that permission to comment licenses a workaround, and that barring the comment pushes the code to the fix, is unmeasured either way. Tan states it from her work on agents (x.com/poteto, 2026-10-13) and puts it into practice in `/no-comments` (github.com/cursor/plugins, `pstack/skills/no-comments/SKILL.md`, revision `2f87c854fe`), which pairs each deletion with a root-cause fix or a type, test or lint [named expert]. Ylikylä, "HACKS.md" (koodihommia.blogspot.com, 2026-01-01) reports the reverse: agents delete hack comments and keep the hacks [named expert]. Self-admitted technical debt research treats the hack comment as the record that lets debt be found: Zampetti, Serebrenik and Di Penta, MSR 2018, DOI 10.1145/3196398.3196423 (20–50% of such comments vanish by accident with their code) [named expert]. The claim sets no default
- `/no-comments`'s keep-list is the one stated form of a strict policy: a licence header; behaviour forced by a dependency, platform or protocol we cannot reshape; a suppression of a faulty or style-only rule; a doc comment that defines a public API contract; an issue or RFC link that explains a constraint code cannot express. A surprise in our own code is not a keep: rename, extract, type or redesign it. Tan, same SKILL.md and `pstack/agents/comment-sicko.md` [named expert]. One source only; it sets no default beyond the first bullet

Not read: *Refactoring*, *A Philosophy of Software Design* and *Clean Code* in full (paywalled); "Characterizing Self-Admitted Technical Debt Generated by AI Coding Agents", DOI 10.1145/3793302.3793588 (HTTP 403); Tan's X posts in full (HTTP 402).

## Suppression and exemption comments

Researched: 2026-11-21 for this section.

- A suppression comment names one rule, gives a reason, and is reported once it suppresses nothing. ESLint, "Configure Rules" (eslint.org: a disable comment takes a `--` description; `reportUnusedDisableDirectives` defaults to warn); Ruff, "The Ruff Linter" (docs.astral.sh/ruff/linter: `# noqa: {code}`; RUF100 reports an unused `noqa`); typescript-eslint, `ban-ts-comment` (`allow-with-description`, `minimumDescriptionLength`, `descriptionFormat`, the only content check found); Biome, "Suppressions" (biomejs.dev: `biome-ignore <rule>: <explanation>`) [standard or field body, each for its own tool]. Google Python Style Guide §2.1 (explain a suppression whose rule name does not) [named expert]
- For many existing findings, keep a committed central baseline, not one inline comment per site, and fail when an entry stops matching. ESLint, "Bulk Suppressions" (`eslint-suppressions.json`; a stale entry exits non-zero, `--prune-suppressions` removes it); Android lint baseline (developer.android.com/studio/write/lint: `lint-baseline.xml`, "only new issues are reported"); Ruff `lint.per-file-ignores` [standard or field body, each for its own tool]. Tool docs alone; the default rests on the next bullet
- A comment that exists only to silence a check is discouraged; a check that needs many exemptions is a faulty check, which its owner fixes or turns off, then makes the clean state an error. Chromium, `docs/clang_tidy.md`, "Ignoring a check" ("comments that exist only to silence clang-tidy" are "actively discouraged"; the comment "should be able to stand on its own even if we removed the `NOLINT`"); Sadowski et al., "Lessons from Building Static Analysis Tools at Google", CACM 61(4), 2018 (fix all existing cases, then enable the check as an error, to "ratchet" quality; under 10% effective false positives) [named expert]. "The comment's presence is the exemption" is not a named anti-pattern in any source

## Decision records

Researched: 2026-11-21 for this section.

- An architecture decision record (ADR) holds one architecturally significant decision: hard to reverse, affecting structure, interfaces, dependencies or construction technique. Nygard, "Documenting Architecture Decisions" (2011); arc42 §9 [standard or field body]; adr.github.io, ASR definition [standard or field body]. An ADR that reads as a policy or a cookbook is an anti-pattern: Zimmermann, "Ten Common Mistakes" (2026, "Blueprint or Policy in Disguise") [named expert]
- An ADR is a page or less, and links to its supporting material. Nygard ("one or two pages"); Fowler, bliki "Architecture Decision Record" (2026-03-24: "typically a single page"); Zimmermann 2026 (context and decision sections "overly verbose") [named expert]
- An ADR names each serious option and why it lost. Zimmermann ("A decision that does not identify alternatives and chooses one of them is not a decision. Period."); Fowler ("list all the serious alternatives ... with their pros and cons"); MADR, "Considered Options" [standard or field body]; AWS Prescriptive Guidance (a rejection keeps its reason "to prevent future discussions") [named expert]
- An ADR lives in source control beside the code it governs. ThoughtWorks Technology Radar, ADRs at Adopt (May 2018: "a record that remains in sync with the code"); Nygard; Google Cloud Architecture Center; Microsoft Azure Well-Architected [named expert]
- The ADR is the conclusion; the discussion lives in an RFC, issue or design doc that it links. Spotify engineering (2020: an RFC first, an ADR once it concludes); MADR (link "issue management systems"); Fowler ("keep a full record of advice separately") [named expert]
- Edit in place or supersede: not settled. Immutable with a superseding ADR: Nygard, Fowler 2026, AWS, Azure ("an append-only log") [named expert]; arc42 and MADR status fields [standard or field body]. Edit in place, or delete: Google Cloud (2024, history in source control), UK Government ADR framework ("Regularly review and update"), Henderson (github.com/joelparkerhenderson/architecture-decision-record: "mutability has worked better"), Zimmermann 2023 ("or even delete them") [named expert]. No source addresses agent readers; two practitioner reports say a superseded ADR misleads an agent that greps or stops early: mattpocock/skills#822 and #1114 [unverified]. The field sets no default here
- A commit message says why one change was made and reads without its links. git `Documentation/SubmittingPatches` ("convey the why behind your change"); Linux kernel `submitting-patches` (a "self-contained" description, background in a `Link:` tag); Google engineering practices, CL descriptions (bug numbers and design-doc links, with "enough context" in case links are not visible later); Beams, "How to Write a Git Commit Message" [named expert]
- A comment that names its issue reaches the ruling where `git blame` cannot, because the deciding change is often not the line's latest commit. Spencer 2021 (stackoverflow.blog, Rules 7 and 8: blame finds only the latest commit, "e.g., moving a method") [named expert]. One source; a measurement here agrees, #5458 §3.4

Not read: ISO/IEC/IEEE 42010:2022 (paywalled).

## In workflow-core

Ruled on the map #5453 (cut code comments to what code cannot say).

- **Comment policy, #5455 (which comment kinds code may carry):** a comment is refused unless it is a permitted kind; when in doubt it goes. Permitted: Tan's five kinds above, with "public API" meaning a contract a party outside the repo relies on (an adopter, a hook runner, a person at the CLI, a tool that reads the output); on a block mixing a foreign fact with our choice built on it, the fact stays and the choice goes; an `ADR-NNNN` site pointer; and a one-line derivation of a chosen value, giving the measurement or the word "guess" and the issue that holds the detail. JSDoc types the type checker reads count as code. Its measured effect: #5470
- **Departure:** the field's experts keep a comment that says why our own code is shaped as it is (Fowler and Beck, Ousterhout; Google engineering practices: "the reasoning behind a decision"); this repo refuses it. Reasons, from this repo's facts: the founder's ruling for a stricter policy (#5455); agent readers over-comment and act on stale comments (bullets above); and the reasoning already has a durable home, the closed issue, reachable from every adopter by one login (#5458 D1). Size of the refused kind: #5455 Q1 re-price
- **Where the reasoning goes, #5457:** to the closed issue by default; to an ADR only under the bar below; to a test, rename, restructure or check where one carries it. The site keeps a bare `#N` or `ADR-NNNN`, no prose, and only where a reader would otherwise undo the code's shape. A test that pins the behaviour may cite the same `#N` beside a descriptive title
- **Exemption comments:** the presence-only markers (`console-kept:`, `spawn-kept:`, `clock-kept:`, the unconsumed-export comment) go, replaced by a code shape, a verified baseline or a hook manifest, following the baseline and ratchet practice above; a `biome-ignore` stays only for a style-only or faulty rule (#5455, #5477)
- **ADRs, #5459:** written only for a decision that is hard to reverse, surprising and a real trade-off, and that concerns architectural shape (a boundary, a cross-module pattern, a lock-in choice). A process rule lives in the shipped skill or doc that sessions act on; a behaviour contract in the module's doc comment. One page or less, with an optional `Options:` line naming each serious alternative and why it lost, and a Status line naming the settling issue
- **Departure:** the closed issue, not the ADR, is the main decision record; reason: every ruling already lands on an issue, and `docs/adr/` does not ship to adopters, so an issue reaches more of its readers (#5458 D1, #1673). ADRs are edited in place and a reversed one deleted, taking the edit-in-place side for agent readers (#5458 D2, lucmoseley/mantahostels#2792). ADRs stay unshipped in each repo's own `docs/adr/`, found by the site pointer and by listing `docs/adr/` in the search-first step (#5459)
