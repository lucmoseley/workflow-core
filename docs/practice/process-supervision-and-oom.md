# process-supervision-and-oom

Researched: 2026-11-08

## Restart policy

- Restart a long-running daemon automatically when it dies. Bercot, s6 overview, skarnet.org/software/s6/overview.html [named expert]; Erlang/OTP, "Supervisor Behaviour", erlang.org/doc/system/sup_princ.html [named expert]; systemd.service(5) `Restart=`, freedesktop.org/software/systemd/man/latest/systemd.service.html, one adopter [unverified]
- Wait between restarts, and grow the wait exponentially to a cap; never restart in a busy loop. s6-supervise, skarnet.org/software/s6/s6-supervise.html ("minimum 1-second delay between two ./run spawns") [named expert]; on client retries, applied to restarts by analogy: Brooker, "Timeouts, retries and backoff with jitter", AWS Builders' Library, builder.aws.com/content/3EumjoZascWd1oZiEgL8ORlv3qE/timeouts-retries-and-backoff-with-jitter [named expert]; Google SRE book, "Addressing Cascading Failures", sre.google/sre-book/addressing-cascading-failures/ [named expert]. In systemd, backoff needs both `RestartSteps=` and `RestartMaxDelaySec=` (v254+; "effective only if RestartMaxDelaySec= is also set"), else the delay stays at `RestartSec=`. systemd.service(5) [standard or field body]
- Cap restarts within a window, then stop and make the failure visible rather than retry forever. Erlang/OTP `intensity`/`period` [named expert]; SRE book ("Don't retry a given request indefinitely", by analogy) [named expert]; s6, a `finish` script exiting 125 stops supervision [named expert]; systemd.service(5) `StartLimitBurst=`/`StartLimitIntervalSec=`, one adopter [unverified]
- Size the window against the delay. systemd's defaults (`RestartSec=` 100 ms; 5 starts per 10 s) stop restarting a unit that crashes at start after about half a second, leaving it failed until a manual or timer start once the interval has passed; and a backoff longer than the window never trips the limit, so it retries forever. Erlang/OTP: choose intensity and period to allow the sustained restart rate you accept [named expert]; systemd.service(5) and systemd-system.conf(5) for the defaults, systemd.unit(5) for the later start [standard or field body]
- `Restart=on-failure` treats SIGTERM as a clean exit on non-oneshot types, so earlyoom's ordinary first signal restarts nothing; `Restart=always` or `RestartForceExitStatus=SIGTERM` brings it back. `Restart=always` is refused on `Type=oneshot`. systemd.service(5) [standard or field body]
- Research: #4141, its 2026-11-08 research comment (issuecomment-6719823472).

## Liveness and timers

- A daemon that can hang without exiting needs a liveness signal that restarts it, and the signal must show real progress and not fire during start-up. Poettering, "systemd for Administrators: Watchdogs", 0pointer.de/blog/projects/watchdog.html [named expert]; Kubernetes, "Liveness, Readiness, and Startup Probes" ("truly indicate unrecoverable application failure") [named expert]; sd_watchdog_enabled(3) and `WatchdogSec=` (armed only once start-up completes) [standard or field body]
- systemd's watchdog wants a ping at half `WatchdogSec=`. sd_watchdog_enabled(3) [standard or field body].
- Spread timer runs with `RandomizedDelaySec=` where many fire together. systemd.timer(5) [standard or field body]; jitter in Brooker, AWS, and the SRE book, by analogy [named expert]
- A timer cannot restart its own target while it is active: an active unit is "not restarted, but simply left running". So a unit reading `active (exited)` needs a separate oneshot that restarts it. freedesktop.org/software/systemd/man/latest/systemd.timer.html [standard or field body]
- `OnUnitInactiveSec=` counts from the unit's last deactivation, so a unit that has never run needs `OnActiveSec=` too, and `AccuracySec=` defaults to 1 minute. Measured on systemd 255, 3 Nov 2026: a 1-minute period fired every 120 s at the default accuracy and every 60-90 s at 30 s. systemd.timer as above [standard or field body]
- `Persistent=` catches up missed runs only on `OnCalendar=` timers, never on monotonic ones. systemd.timer as above [standard or field body]
- Timers over cron rests on blog comparisons alone (trstringer.com/systemd-timer-vs-cronjob/, adminschoice.com/systemd-timers-vs-cron/), so it sets no default [unverified].
- Derived: a timer that reads the daemon's own lock covers every way the daemon was started, including outside any unit. One repo's choice, so it sets no default [unverified]
- Research: #4141, its 2026-11-08 research comment (issuecomment-6719823472).

## OOM ranking and recovery

- Kill in user space, on memory pressure, before the kernel OOM killer acts; the kernel's is a last resort that runs only once the machine is thrashing. Facebook oomd, github.com/facebookincubator/oomd [named expert]; earlyoom README, github.com/rfjakob/earlyoom [named expert]; Hocko on LKML, lkml.indiana.edu/hypermail/linux/kernel/1908.1/01539.html ("last resort") [named expert]; Weiner, PSI, docs.kernel.org/accounting/psi.html [named expert]; systemd-oomd.service(8), one adopter [unverified]
- Shield only the few daemons whose loss breaks the machine with a negative `oom_score_adj`, keeping -1000 for those that must never die. Kernel `Documentation/filesystems/proc.rst` (-1000 disables OOM killing; the value "polarize[s]" the choice) [standard or field body]; systemd.resource-control(5) ("use avoid and omit sparingly", said of `ManagedOOMPreference=` and applied here by analogy) [named expert]; systemd's shipped units (udevd -1000, journald -250), one adopter [unverified]
- Rank a supervisor below its children, so a kill takes a service, not what restarts it. systemd-user.conf(5): service processes default to the manager's value "plus 100", "slightly more likely to be killed ... than the manager itself"; systemd v250 NEWS, github.com/systemd/systemd/blob/main/NEWS [named expert]; Erlang/OTP supervision trees [named expert]
- `oom_score_adj` is inherited at fork, so a negative `OOMScoreAdjust=` on a process that spawns others shields them too. systemd.exec, freedesktop.org/software/systemd/man/latest/systemd.exec.html, sets the value per unit [standard or field body]; the inheritance was measured here on kernel 6.18, 8 Nov 2026 (a child read its parent's raised value), one probe [unverified]. earlyoom ranks by `/proc/*/oom_score`, which carries the adjustment, so the value shields from earlyoom as well as the kernel; earlyoom README [standard or field body]. The floor is "the last value set by a CAP_SYS_RESOURCE process", so an unprivileged process can raise its value but not lower it below that, and the value has to come from the unit. Kernel proc.rst [standard or field body]
- Design every daemon to be killed at any time and expect a restart after any kill: earlyoom kills "until it is above the minimum again". Candea and Fox, "Crash-Only Software", HotOS 2003 ("stop=crash and start=recover") [named expert]; earlyoom README, for its kill loop [standard or field body]; earlyoom's upstream unit ("have systemd restart it should it get killed for some reason. Restart=always"), one adopter [unverified]
- Derived: `OOMPolicy=` acts on kernel and systemd-oomd kills, which systemd sees as cgroup events, and not on earlyoom's plain signals. Read from systemd.service(5), not tested, so it sets no default [unverified]
- Research: #4141, its 2026-11-08 research comment (issuecomment-6719823472).

## A daemon taking up new code

- An upgrade loses no connection or state, and a new version that fails to start leaves the service up. Bauer, "Graceful upgrades in Go", blog.cloudflare.com/graceful-upgrades-in-go/ ("new process can crash during initialisation, without bad effects") [named expert]; Poettering, socket activation, 0pointer.de/blog/projects/socket-activation.html ("Not a single connection is lost") [named expert]; systemd.io/FILE_DESCRIPTOR_STORE/ [named expert]. Two routes: run old and new side by side, rolling back to the old if the new fails, as nginx `USR2` (the old master "does not close its listen sockets"; a failing new master is sent `TERM` and the old carries on; nginx.org/en/docs/control.html), HAProxy `-x`/`-sf` (docs.haproxy.org/2.8/management.html) and Envoy hot restart (envoyproxy.io/docs/envoy/latest/intro/arch_overview/operations/hot_restart) do [unverified]; or let the manager hold the sockets and state so the old process may stop first, as systemd's socket activation and fd store do.
- Carry state across a restart or re-exec explicitly, in a store outside the process. systemd.io/FILE_DESCRIPTOR_STORE/ [named expert]; Candea and Fox ("dedicated state stores") [named expert]; systemctl(1) `daemon-reexec` will "serialize the manager state, reexecute the process and deserialize the state again", and `FileDescriptorStoreMax=` in systemd.service(5), one adopter [unverified]
- One upgrade at a time: tableflip's README states "Only a single upgrade is ever run in parallel". Bauer, Cloudflare blog [named expert]; tableflip README, github.com/cloudflare/tableflip, and nginx refusing a second `USR2`, two adopters [unverified].
- Node's `process.execve(file, args, env)` (v23.11.0, Stability 1) replaces the image under the same pid "without triggering any exit or close events" and keeps only stdin, stdout and stderr; a failed `execve(2)` throws and "the current process continues to run with its state unchanged". So any cleanup runs first, and any other open handle is reopened by the new image. nodejs.org/api/process.html §process.execve [standard or field body]
- Research: #4141, its 2026-11-08 research comment (issuecomment-6719823472).
