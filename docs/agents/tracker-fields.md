# Tracker fields — the producer/consumer contract

Every structured field written into the GitHub issue tracker, who writes it and what reads it.

A vendored skill can write a structured field into the tracker with nothing required to read it. **A row here with a producer and no consumer is the bug.** When a skill starts writing a new field, add its row and name the consumer — if none exists, write one or stop emitting the field.

| Field | Written by | Read by |
|---|---|---|
| `<card-id> — <title>` title prefix | Whoever opens a card issue (by hand) | `/card-close` step 2; `check-issue-card-drift.js` |
| `## Acceptance criteria` checkboxes | `/to-tickets` | `docs/agents/issue-tracker.md` §Closing an issue with acceptance criteria; `check-ticket-criteria.js` |
| Native sub-issue link (parent) | `/to-tickets`, `/wayfinder`, and by hand on any issue created mid-session (`docs/agents/issue-tracker.md` §Placing a new issue) | `/wayfinder` frontier query; `check-issue-orphans.js` |
| Native `blocked_by` dependency | `/to-tickets`, `/wayfinder`, and by hand for cross-map edges | `/wayfinder` frontier query; for cross-map edges, the GitHub UI's blocked indicator (`docs/agents/issue-tracker.md` §Two dependency graphs) |
| `kind:spec` / `kind:ticket` | `/to-spec`, `/to-tickets`, and by hand on a ticket added to a spec mid-session | `check-ticket-criteria.js` (scoping); `check-issue-labels.js`; `docs/agents/triage-labels.md` rules |
| Four state labels (`needs-info`, `ready-for-agent`, `ready-for-human`, `wontfix`) | None — **this repo has no state labels** (mantahostels#235); the vendored roles map to a `takes:` value or a close reason (`docs/agents/triage-labels.md`, the table at the top) | — |
| `takes:*` labels | Whoever creates or triages the issue; `scripts/guard-issue-create-label.js` **denies** a `gh issue create` that carries no valid value (mantahostels#470), and `scripts/place-new-issue.sh` asks at creation, once per issue created rather than once per prompt (mantahostels#314, the issue a per-prompt ask left unlabelled) | Whoever picks the command to open the issue with (`docs/agents/triage-labels.md` §`takes:`); `check-issue-labels.js`, in the daily repo-checks run at session start (#1557); `pick-next.js` (its TAKES column) — both mantahostels#227 |
| `**Gated until:** YYYY-MM-DD — <why>` body line | The founder, or a session applying the founder's ruling, once an issue's next action is a date rather than a piece of work (mantahostels#85, no working channel to an outside partner) — **and only where that date is within 14 days** (`docs/agents/issue-tracker.md` §Gating an issue: a date, a condition, or a close onto the card) | `scripts/pick-next.js`: holds the issue out of the shortlist until that date and prints it under GATED, and under the waiting banner too where the issue also carries `waiting:external`. Fails open — a lapsed date, an unreadable one, and a body that also carries the `**Gated on:**` row below each gate nothing and say so |
| `**Gated on:** <condition> — check: <command> — abandon if: <clause>` body line | The founder, or a session applying the founder's ruling, once an issue waits on a data condition rather than a date — the whole point being not to guess a date that lies about what is being waited for (mantahostels#1419). `— check:` is optional, for a condition no single command tests; `abandon if:` is required, being the only thing that ever retires a condition nobody will meet | `scripts/pick-next.js`: holds the issue out of the shortlist, states the condition in its exclusion reason, and prints the line verbatim under GATED beside the date gates, interleaved by issue number. **Nothing evaluates the condition** — the `check:` is the reader's to run. Fails open — a line missing its abort clause, and a body carrying both gate markers, each gate nothing and say so, in the printed banner and in `--json`'s `bothMarkers` alike |
| `**Gate basis:** <data, and why nothing sooner fits>` body line | Whoever writes the `**Gated until:**` or `**Gated on:**` line, directly beneath it (#577) | `scripts/check-issue-labels.js`: a WARN, NO-GATE-BASIS, on an open issue whose well-formed gate line has no basis or an empty one. Never un-gates — `scripts/lib/issue-gate.js` returns it as `resolveGate()`'s `basis`, which no hold reads |
| `waiting:external` label | Whoever hands the work off outside the project, at the moment it is sent — the founder, or a session that sent the thing itself or has the founder's word that it was sent (#869): an application submitted, an email sent. No script guesses the label: `scripts/park-blocked.sh` applies the value its calling session names, and mantahostels#101 bars `pick-next.js` from writing at all | `scripts/pick-next.js`: elapsed days from the timeline's `labeled` event, shown in its WAIT column, raising rank once the wait reaches 7 days, and never demoting or filtering (mantahostels#243, mantahostels#259, mantahostels#956) |
| `wayfinder:*` labels | `/wayfinder` charting, and **by hand on any ticket spun off a map mid-session** (mantahostels#134 and mantahostels#135 were created unlabelled that way) | `/wayfinder` map and frontier queries; `check-issue-labels.js` |
| Assignee (the claim) | The session working the issue right now, per `docs/agents/issue-tracker.md` §Claiming — never a session that merely creates it for later | `/wayfinder` frontier query, via `scripts/wayfinder-frontier.js` (mantahostels#702), and `scripts/pick-next.js` (mantahostels#645) — each drops it only where a live arbiter claim backs it; `scripts/check-stale-claims.js` (a claim held with nothing since); the human, for who did what |
| Arbiter issue claim (`session-arbiter.js claim-issue <n>`) | The session working the issue, alongside the assignee — per `docs/agents/issue-tracker.md` §Claiming; `scripts/record-issue-claim.js` writes it automatically when the assignment runs through the Bash tool (mantahostels#646) | `scripts/pick-next.js` (mantahostels#645); `scripts/wayfinder-frontier.js`, which is what `/wayfinder`'s frontier query reads (mantahostels#702) |
| `**Deviations:**` comment | `/implement`, before it dispatches the review, where the build departed from what the issue asked — an *input* to review, where `**Outstanding:**` is its output (mantahostels#1242) | `/code-review`'s Spec sub-agent, which reports it under `## Declared departures`, separate from findings and never suppressed; the parent pastes it in, so `/implement` gets the reading rule too. Both halves from `scripts/guard-dispatch.js` (its `guard-review-rules` core) when code-review loads as a skill (mantahostels#3451); a typed `/code-review` takes the reading half from `scripts/inject-tracker-docs.sh` |
| `**Outstanding:**` line | Whichever command closes the issue, in the resolution comment; its content comes from `/code-review`'s finding dispositions | `guard-issue-close.js` and `resolve-ticket.js`, at the close — the line's grammar and each cited issue open, never the prose around it (#984) |
| `**Practice:**` line | Whichever command resolves the issue, in the resolution comment — the Leading practice call as `ran`, `covered`, `skipped` or `none-fits`; its form unchecked (#2325) | `resolve-ticket.js`, which refuses a completed resolution without it |
| `**Values:**` line | Whichever command resolves the issue, in the resolution comment — each house or untraced value it relies on, or `none`; `resolve-ticket.js` refuses a completed resolution without it (#1707). An audit rewrites an entry in place as `traced:` | A rule-2 audit's search of the trackers for `untraced` (#1701) |
| `**Census:**` line | Whichever command resolves the issue, in the resolution comment, where the ticket's commits changed what a census-measured guard prints and its row is left un-re-anchored — why, and which ticket owns the re-measure (#1876) | `resolve-ticket.js`, which refuses a completed resolution over such a row without it |
| `**Unlanded:**` line | Whichever command resolves the issue, in the resolution comment, where a commit citing the ticket or named by sha is not on the pushed ref (`origin/landing` with the `landing` module on) under its hash or subject — why the close stands without it, such as a neighbour's cite in passing (#3101) | `resolve-ticket.js` and `guard-issue-close.js`, which refuse a completed close over such a commit without it |
| `manual-finding` label | Any session that finds a fact in `docs/operating-manual.md` wrong and cannot land it under `manual-sync`'s targeted-correction mode, so files an issue instead (mantahostels#27) | `manual-sync`'s findings intake, at the top of every full run (mantahostels#189) |
| Issue closed state | `/card-close`, `/wayfinder`, `/triage` | `check-issue-card-drift.js`; `check-ticket-criteria.js` |
| §B's entry count and trailing-7-day entries/day rate, in the §B budget issue's body | `scripts/report-doc-map-budget.js`, on the same daily refresh that writes the rest of mantahostels#1079's body — a reported figure only, no threshold and no trigger (mantahostels#1347, the level signal mantahostels#1316 adopted) | Whoever reads back mantahostels#1728’s admission-rate prediction. ⚠ **The rate is broken** (-0.1/day reported against +15.75/day measured); mantahostels#1704 owns it |
| `Archive: closed children of #<map>` title | `scripts/archive-closed-children.js`, on the archival container it creates the first time a map needs one (#92) | The same script, on every later run — how it finds the existing container instead of making a second one |

**Never filter closed issues by a label a close does not clear.** No command strips a label on close, so a `takes:` value on a closed issue says what someone would have typed, not what is true now.
