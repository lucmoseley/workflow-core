**Where the `roadmap` module is on**, GitHub Issues holds what is being worked on **now**; the roadmap is the backlog, taken when it makes sense. An issue whose wait fires when a card is taken there **closes, with a `card:<card-id>` label applied naming that card, and is re-filed when the card is taken** by querying `gh issue list --state closed --label card:<id>` (mantahostels#1048, mantahostels#3291, mantahostels#3320). Where it is off, the tracker is the only backlog and a gated issue stays open.

| The gate | What to do |
|---|---|
| A **calendar date**, however far away | Keep the issue open, carrying `**Gated until:** YYYY-MM-DD — <why>`, its `**Gate basis:**` warranting the date (#5401 Q1). `scripts/pick-next.js` holds it out of the shortlist until that date and prints it under GATED |
| A **data condition you can state in a sentence** | Keep the issue open, carrying `**Gated on:** <condition> — abandon if: <what makes the ticket not worth doing>`, and `— check: <command>` between the two where one command tests it. The command must print what it saw: one that answers only through its exit code ends in `&& echo "<met>" || echo "<unmet>"`, and `file-issue.js` and `issue-body.js` refuse one that prints nothing, running it in the checkout of the repo whose issue it gates and refusing where there is none, where a raw `gh issue create` only warns (#3487). It reads GitHub live, never another checkout's `origin/` ref, which nothing fetches: every route, a raw `gh issue create` included, refuses a `git -C <dir> … origin/` read that no `git -C <dir> fetch` precedes, and an adopter's pin reads through `node scripts/release-contains.js <sha> --pinned-by <owner/repo>` (#5697). `scripts/pick-next.js` holds it out of the shortlist and prints the line verbatim under GATED, evaluating nothing (mantahostels#1329, mantahostels#1330). Two routes judge it (#2279): `/pick-next` runs `scripts/check-gates.js --issue <n>` on each GATED row; the refill loop sweeps every gate on its own cadence and launches `/triage <n>` on a changed reading or repair state, and on a gate with no `check:` at its first sweep and every 14 days after (lucmoseley/mantahostels#3869). On met, the judge comments the evidence and strips the marker; no exit code is a verdict (mantahostels#1332). **A question about a rate gets a count gate** — `**Gated on:** N <events> — check: <cmd>` — so `check-gates` releases it when the count is met, never on a calendar date (#4946) |
| A wait that **fires when a roadmap card is taken** (the `roadmap` module on) | Close it, having first applied the `card:<card-id>` label naming that card |
| A gate you cannot state as a date or a condition | Rewrite it until it reads as one |

**The founder typing a `/`-command is never a condition** — a dispatched session types it too, so the gate only stops dispatch. Relabel to that command's `takes:` value instead; `scripts/check-issue-labels.js` reports the shape as COMMAND-GATE (#411).

**Each gate line carries a `**Gate basis:**` line on its own line directly beneath it** — a window inside a condition ("4 weeks of data") included, and on a gate added to an existing issue as much as a new one. **A wait written as prose — `after a week live`, `the week after`, `24 h have run since`, `no earlier than` — owes the same line**. The window is the shortest the data defends. The line's template: `**Gate basis:** <claim, one-sided>; baseline <k>/<N> (<rate>, <source, date range>); target <the baseline point | a stated SLO or fixed target, with its source>; <C>% one-sided, <method>; pass = <r> events in n = <n> <unit> (<expected time> at <events per day>); fail at event <r+1>; time floor <none | cycle and length>; assumes <independence, same population>`. **Where the body writes a window, the basis carries one of three warrants**: a count derivation — a baseline `k/N`, a target, the count that results, and a source; a named cycle (daily, weekly, weekday and weekend, a cron or sweep cadence) with a measured figure and a source; or another issue cited for what sets the window, never only as the event it starts from, which stands only where that issue's own live basis names the same window and carries a count or cycle warrant of its own, or where the citation names a founder question round the issue holds (`#1556 Q4`; #5007). A source is another issue, a commit sha, a repo path or a code-spanned command. Where the ticket names no bound, the confidence is 95% one-sided (#2411). **A before/after rate question is tested against the baseline point with a two-sample exact test**: the conditional Poisson test for events over time (as R's `poisson.test` does), one-sided Fisher for events per trial. With zero events after and α = 1 − the confidence, the window is T2 = T1 × (α^(−1/k) − 1) for a baseline of k events in T1, and for trials the least n with C(N,k) ÷ C(N+n,k) ≤ α. Sizing n against a fixed target by the exact binomial with zero events (the rule of three) is only for a question against a stated SLO or fixed target. Worked example: `**Gate basis:** the leap rate per VM boot after the install is below the baseline's; baseline 3/30 VM boots (10.0%, #4081, 3 Nov 2026); target the baseline point; 95% one-sided, one-sided Fisher (C(30,3) ÷ C(30+n,3) ≤ 0.05); pass = 0 leaps in n = 50 boots (about 33 days at 1.5 boots a day); fail at the first leap; time floor none; assumes independent boots, the same population as the baseline's`. **A model also reads each body the create guard, `file-issue.js` and `issue-body.js` write** (`scripts/lib/gate-judge.js`, #4964), asking what each wait hangs on and how each basis sets its window. A fault it raises refuses the write as a pattern fault does, the refusal saying the model reading raised it (#4970). Where the reading is wrong, write a live body line `**Gate judge override:** <why the reading is wrong>`: with a reason it clears every fault of the model reading on that body and no pattern fault, and `scripts/check-issue-labels.js` lists each open issue carrying one as GATE-JUDGE-OVERRIDE for review. A review that finds the override right adds `**Gate judge override reviewed:** <key> — <date> — <where the review is recorded>` beneath it, the key the WARN prints; it silences the WARN until the reason is edited (#5673), and the three write routes refuse one written in the same write that adds or edits its override (#5674). Where the model cannot run, one line says so and the patterns alone judge the write. **Enforced at write time** (#672, #823, #4946): the create guard, `file-issue.js` and `issue-body.js`'s command line refuse a body adding a gate line or prose wait with no basis, adding a window — a count and a unit, an `abandon if:` clause's included — that its basis does not name, adding a basis with no warrant beneath a window, or adding a basis whose own figures do not give the window it states, an old basis included where the edit adds or changes a gate line; `issue-body.js` knows the issue's number, so there a basis citing its own ticket cites nothing. The patterns check the basis names each window and carries a warrant, and `scripts/lib/gate-window.js` recomputes the window of a basis naming its method (conditional, Fisher, or exact binomial against its target), a `k/N` baseline, a `<C>% one-sided` and a `pass = 0 … n = <n>` in the baseline's unit, leaving any other basis to the warrant check; the GraphQL create, and a REST create repeating its `body` field, pass it unjudged. `file-issue.js` and `issue-body.js` print this rule whenever a write adds a gate line. A faulty basis on an existing body still gates; `scripts/check-issue-labels.js` reports each fault on an open gate — no basis, an unnamed window, no warrant, a window its own figures do not give — as NO-GATE-BASIS (#577).
