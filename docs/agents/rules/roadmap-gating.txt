GitHub Issues holds what is being worked on **now**; the roadmap is the backlog, taken when it makes sense. An issue gated on a distant *date* therefore **closes, with a `card:<card-id>` label applied naming the card that will fire it, and is re-filed when that card is taken** by querying `gh issue list --state closed --label card:<id>` (mantahostels#1048, mantahostels#3291, mantahostels#3320).

| The gate | What to do |
|---|---|
| A calendar date **within 14 days** | Keep the issue open, carrying `**Gated until:** YYYY-MM-DD — <why>`. `scripts/pick-next.js` holds it out of the shortlist until that date and prints it under GATED |
| A **data condition you can state in a sentence** | Keep the issue open, carrying `**Gated on:** <condition> — abandon if: <what makes the ticket not worth doing>`, and `— check: <command>` between the two where one command tests it. The command must print what it saw: one that answers only through its exit code ends in `&& echo "<met>" || echo "<unmet>"`, and `file-issue.js` and `issue-body.js` refuse one that prints nothing, running it in the checkout of the repo whose issue it gates and refusing where there is none, where a raw `gh issue create` only warns (#3487). `scripts/pick-next.js` holds it out of the shortlist and prints the line verbatim under GATED, evaluating nothing (mantahostels#1329, mantahostels#1330). Two routes judge it (#2279): `/pick-next` runs `scripts/check-gates.js --issue <n>` on each GATED row; the refill loop sweeps every gate on its own cadence and launches `/triage <n>` on a changed reading or repair state. On met, the judge comments the evidence and strips the marker; no exit code is a verdict (mantahostels#1332). **A question about a rate gets a count gate** — `**Gated on:** N <events> — check: <cmd>` — so `check-gates` releases it when the count is met, never on a calendar date (#4946) |
| A date **beyond 14 days**, or a gate you cannot state as a condition at all | Close it, having first applied the `card:<card-id>` label naming the card that will fire it |

**The founder typing a `/`-command is never a condition** — a dispatched session types it too, so the gate only stops dispatch. Relabel to that command's `takes:` value instead; `scripts/check-issue-labels.js` reports the shape as COMMAND-GATE (#411).

**Each gate line carries a `**Gate basis:**` line on its own line directly beneath it** — a window inside a condition ("4 weeks of data") included, and on a gate added to an existing issue as much as a new one. **A wait written as prose — `after a week live`, `the week after`, `24 h have run since`, `no earlier than` — owes the same line**. The window is the shortest the data defends. The line's template: `**Gate basis:** <claim, one-sided>; baseline <k>/<N> (<rate>, <source, date range>); target <value> (<why: baseline point | baseline lower bound | stated SLO>); <C>% one-sided, <method>; pass = <r> events in n = <n> <unit> (<expected time> at <events per day>); fail at event <r+1>; time floor <none | cycle and length>; assumes <independence, same population>`. **Where the body writes a window, the basis carries one of three warrants**: a count derivation — a baseline `k/N`, a target bound, the count that results, and a source; a named cycle (daily, weekly, weekday and weekend, a cron or sweep cadence) with a measured figure and a source; or another issue cited for what sets the window, never only as the event it starts from. A source is another issue, a commit sha, a repo path or a code-spanned command. Where the ticket names no bound, the default is 95% one-sided, the target the baseline's one-sided 95% lower bound, by the exact binomial with zero events (the rule of three). Worked example: `**Gate basis:** refusal rate after the fix is below the baseline's lower bound; baseline 27/449 attempts (6.0%, #4855, 5–10 Nov); target 4.28% (the baseline's one-sided 95% lower bound); 95% one-sided, exact binomial; pass = 0 refusals in n = 69 attempts (about 8 hours at 200 attempts a day); fail at the first refusal; time floor none; assumes independent attempts, same mix as the baseline`. **Enforced at write time** (#672, #823, #4946): the create guard, `file-issue.js` and `issue-body.js`'s command line refuse a body adding a gate line or prose wait with no basis, adding a window — a count and a unit, an `abandon if:` clause's included — that its basis does not name, or adding a basis with no warrant beneath a window; `issue-body.js` knows the issue's number, so there a basis citing its own ticket cites nothing. It checks the basis names each window and carries a warrant, never that it holds up; the REST and GraphQL creates pass it unjudged. `file-issue.js` and `issue-body.js` print this rule whenever a write adds a gate line. A faulty basis on an existing body still gates; `scripts/check-issue-labels.js` reports each fault on an open gate — no basis, an unnamed window, no warrant — as NO-GATE-BASIS (#577).
