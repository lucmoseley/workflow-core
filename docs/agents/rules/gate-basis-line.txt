The line's template: `**Gate basis:** <claim, one-sided>; baseline <k>/<N> (<rate>, <source, date range>); target <the baseline point | a stated SLO or fixed target, with its source>; <C>% one-sided, <method>; pass = <r> events in n = <n> <unit> (<expected time> at <events per day>); fail at event <r+1>; time floor <none | cycle and length>; assumes <independence, same population>`. **Where the body writes a window, the basis carries one of three warrants**: a count derivation — a baseline `k/N`, a target, the count that results, and a source; a named cycle (daily, weekly, weekday and weekend, a cron or sweep cadence) with a measured figure and a source; or another issue cited for what sets the window, never only as the event it starts from, which stands only where that issue's own live basis names the same window and carries a count or cycle warrant of its own, or where the citation names a founder question round the issue holds (`#1556 Q4`; #5007). A source is another issue, a commit sha, a repo path or a code-spanned command. Where the ticket names no bound, the confidence is 95% one-sided (#2411). **A before/after rate question is tested against the baseline point with a two-sample exact test**: the conditional Poisson test for events over time (as R's `poisson.test` does), one-sided Fisher for events per trial. With zero events after and α = 1 − the confidence, the window is T2 = T1 × (α^(−1/k) − 1) for a baseline of k events in T1, and for trials the least n with C(N,k) ÷ C(N+n,k) ≤ α. Sizing n against a fixed target by the exact binomial with zero events (the rule of three) is only for a question against a stated SLO or fixed target. Worked example: `**Gate basis:** the leap rate per VM boot after the install is below the baseline's; baseline 3/30 VM boots (10.0%, #4081, 3 Nov 2026); target the baseline point; 95% one-sided, one-sided Fisher (C(30,3) ÷ C(30+n,3) ≤ 0.05); pass = 0 leaps in n = 50 boots (about 33 days at 1.5 boots a day); fail at the first leap; time floor none; assumes independent boots, the same population as the baseline's`. **A model also reads each body the create guard, `file-issue.js` and `issue-body.js` write** (`scripts/lib/gate-judge.js`, #4964), asking what each wait hangs on and how each basis sets its window. A fault it raises refuses the write as a pattern fault does, the refusal saying the model reading raised it (#4970). Where the reading is wrong, write a live body line `**Gate judge override:** <why the reading is wrong>`: with a reason it clears every fault of the model reading on that body and no pattern fault, and `scripts/check-issue-labels.js` lists each open issue carrying one as GATE-JUDGE-OVERRIDE for review. A review that finds the override right adds `**Gate judge override reviewed:** <key> — <date> — <where the review is recorded>` beneath it, the key the WARN prints; it silences the WARN until the reason is edited (#5673). Where the model cannot run, one line says so and the patterns alone judge the write.
