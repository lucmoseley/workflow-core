The line's template: `**Gate basis:** <claim, one-sided>; baseline <k>/<N> (<rate>, <source, date range>); target <value> (<why: baseline point | baseline lower bound | stated SLO>); <C>% one-sided, <method>; pass = <r> events in n = <n> <unit> (<expected time> at <events per day>); fail at event <r+1>; time floor <none | cycle and length>; assumes <independence, same population>`. **Where the body writes a window, the basis carries one of three warrants**: a count derivation — a baseline `k/N`, a target bound, the count that results, and a source; a named cycle (daily, weekly, weekday and weekend, a cron or sweep cadence) with a measured figure and a source; or another issue cited for what sets the window, never only as the event it starts from. A source is another issue, a commit sha, a repo path or a code-spanned command. Where the ticket names no bound, the default is 95% one-sided, the target the baseline's one-sided 95% lower bound, by the exact binomial with zero events (the rule of three). Worked example: `**Gate basis:** refusal rate after the fix is below the baseline's lower bound; baseline 27/449 attempts (6.0%, #4855, 5–10 Nov); target 4.28% (the baseline's one-sided 95% lower bound); 95% one-sided, exact binomial; pass = 0 refusals in n = 69 attempts (about 8 hours at 200 attempts a day); fail at the first refusal; time floor none; assumes independent attempts, same mix as the baseline`.
