COMMIT BY PATHSPEC, NEVER `git add` FIRST.

  node scripts/commit-paths.js -m "…" -- <paths>   (Bash `timeout: 600000`)

It intent-adds new paths, refuses a typo, an ignored path or a directory
hiding new files, and waits out a neighbour's index lock. Exits: 0 done,
1 lock held — re-run, 2 fix the input, 3 git or a hook refused. The hand form
stays legal:

  git commit -m "…" -- <paths>

The index is repo-global. Between a `git add` and its commit, a parallel
session's commit sweeps your staged files in under its message (mantahostels#63).
A merge or rebase is the one place staging is unavoidable: stage and commit
there in one uninterrupted step.

By hand, a file git does not track yet needs `git add -N <path>` first: a
pathspec cannot reach it, and git exits 1 having committed nothing.

THE WORKING TREE IS A SECOND HAZARD. A pathspec takes the working-tree copy of
every path it names, a live neighbour's unsaved edits included (mantahostels#1539).
Commit your own paths and leave theirs. Sharing a file with them? `--patch`
commits your lines alone (docs/agents/partial-commit.md).

WHAT THE GUARD DOES NOT CATCH. Its warns are advisory — the commit lands — so
read the index yourself before committing. It stands down mid-merge, rebase,
cherry-pick or revert, and in a worktree, except the `--no-verify` deny and the
untracked-pathspec warn, which bind everywhere. And a commit run from your own
terminal, from a script, or in a worktree never reaches the hook at all.
